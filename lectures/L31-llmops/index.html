第 31 讲 · 评估、监控与 LLMOps — 从能用到可靠 ​

上一讲你学会了和 AI 一起写代码——但代码写出来 ≠ 产品可以上线。

本讲将 L26 PGE 框架中的 Evaluator 升级为生产级评估体系，同时呼应从 L03 到 L26 的整条 Evaluator 线。

一个幻觉率 5% 的模型在实验室是论文，在生产环境是事故——"能用"和"可靠"之间隔着整个工程体系。模型是引擎，LLMOps 是整辆车。

2024-2026 年 LLMOps 从 "DevOps 的子集" 演化为独立学科——LangSmith / Helicone / Langfuse / Braintrust / OpenLLMetry 等专用工具生态崛起。这是 LLM 应用从 "做出来" 到 "做得起" 的关键基础设施。

前置知识核心产出建议用时
L03（损失函数）、L18（RLHF）、L20（推理）、L24（RAG）、L26（PGE）① 理解推理服务化（vLLM / PagedAttention / Continuous Batching / Speculative Decoding）② 掌握生产硬指标（TTFT / TPS / KV Cache 利用率） ③ 构建五层评估体系 ④ 理解可观测性系统（Prompt 版本 / 成本 / Trace） ⑤ 掌握幻觉治理三板斧 ⑥ 看 2026 年 LLMOps 工具链 ⑦ 拿到 L34 (Safety) 的伏笔阅读 ~80 分钟 + 动手 ~30 分钟

从上一讲到这一讲 ​

第 30 讲问：这个应用你敢直接上线吗？隔着整个工程体系。

你学会了和 AI 一起写代码——Claude Code 帮你建应用，Copilot 帮你补全，Cursor 帮你重构。但现在你要面对一个残酷的现实：某公司用 LLM 做客服，上线第一天，AI 向 40 多个用户承诺了根本不存在的退款——幻觉率只有 3%，但 3% 意味着每 33 次对话就有一次胡说八道。在实验室，3% 是一个可以发论文的数字；在生产环境，3% 是每小时几十次事故。

从"能用"到"可靠"之间隔着什么？一整套工程体系：推理服务、性能指标、评估流水线、可观测性、幻觉治理。这套体系叫 LLMOps。

1. 推理服务化：让模型跑起来 ​

1.1 为什么 model.generate() 不够 ​

一个 model.generate() 调用在你的笔记本上跑得通，但生产环境要面对：并发（100 个用户同时请求）、延迟（用户等不了 30 秒）、成本（GPU 一小时几十块钱，空跑就是烧钱）、可用性（挂了要能自动恢复）。

核心概念

推理服务化（Inference Serving）的核心问题是：如何让一个几十 GB 的模型高效地同时服务成百上千个用户？ 关键技术是 PagedAttention（内存管理）、Continuous Batching（动态批处理）和 Speculative Decoding（投机解码）。

1.2 PagedAttention（vLLM 的核心） ​

核心概念

PagedAttention 把 KV Cache 像操作系统的虚拟内存一样分页管理。 传统推理预分配最大长度的 KV Cache（如 4096 token），即使实际只用了 100 token——浪费率高达 97%。PagedAttention 按需分配物理内存页，用逻辑→物理映射表避免浪费。

传统方式:
  请求 A（实际 100 token）→ 预分配 4096 token 内存 → 浪费 97%
  请求 B（实际 200 token）→ 预分配 4096 token 内存 → 浪费 95%
  GPU 内存满 → 只能同时服务 2 个请求

PagedAttention:
  请求 A（100 token）→ 分配 7 页（每页 16 token）→ 112 token 内存
  请求 B（200 token）→ 分配 13 页 → 208 token 内存
  GPU 内存充裕 → 可以同时服务 20+ 个请求

直觉

传统方式像给每位客人预留一整张大桌子（8 人桌），即使只来了 1 个人。PagedAttention 像自助餐厅的灵活座位——来几个人坐几个位子，空椅子留给其他客人。

1.3 Continuous Batching 与 Speculative Decoding ​

Continuous Batching（连续批处理）：不是凑齐一批请求再一起处理，而是一有请求就"插队"加入当前 batch。完成的请求立即退出，新请求立即加入——GPU 利用率大幅提升。

Speculative Decoding（投机解码）：用一个小模型（Draft Model）快速生成候选 token，再让大模型并行验证。如果小模型猜对了（大部分情况），相当于一次大模型推理完成了多个 token——延迟显著降低。

传统解码:  大模型 → token₁ → 大模型 → token₂ → 大模型 → token₃
          (每个 token 一次大模型调用)

投机解码:  小模型快速生成 [t₁, t₂, t₃, t₄, t₅]
          大模型一次验证 → 接受 [t₁, t₂, t₃]，拒绝 t₄
          (5 个候选 token 只用了 1 次大模型调用 + 1 次小模型调用)

2. 生产硬指标 ​

核心概念

三个核心指标定义了推理服务的"好不好"：TTFT（首 token 时间）、TPS（每秒 token 数）、KV Cache 利用率。 这些指标直接对应用户体验和运营成本。

图：推理延迟分布示意——关注 P95/P99 尾延迟，而非平均值。

指标含义用户感知优化目标
TTFT (Time To First Token)用户按发送到看到第一个字的时间"AI 反应快不快"< 500ms（对话场景）
TPS (Tokens Per Second)流式输出的速度"AI 说话流不流畅"> 30 TPS（阅读速度）
KV Cache 利用率GPU 显存中 KV Cache 的有效利用比运营成本> 85%（PagedAttention）

推理经济学

训练是一次性成本，推理是持续成本。一个 70B 模型在 A100 上的推理成本约 $2-4/小时。如果 KV Cache 利用率从 30% 提升到 90%（通过 PagedAttention），同一块 GPU 可以服务 3 倍的并发请求——等于推理成本降低到 1/3。推理优化不是锦上添花，是生存问题。

图：LLM 推理成本瀑布——模型大小、量化方案、batch 策略层层影响最终每请求成本。

3. 评估体系：五层渐进 ​

3.1 Evaluator 线的终极呼应 ​

[!abstract] Evaluator 线回顾

  • L03 损失函数：最原始的 Evaluator——数值越小越好
  • L18 RLHF 奖励模型：人类偏好训练的 Evaluator——给回答打分
  • L20 推理模型内置验证：模型自己做 Evaluator——思维链中的自我检查
  • L26 PGE 显式化：Agent Loop 中的 Evaluate 步骤——外部信号反馈
  • L31 生产级 Evaluator（本节）：LLM-as-Judge + 评估流水线 + 人工抽检——完整的质量保障体系

3.2 五层评估架构 ​

第 5 层: Agent 评估（SWE-bench / TAU-bench）
         → 端到端任务完成率
第 4 层: Benchmark 评估
         → 标准数据集上的量化指标
第 3 层: 人工评估
         → 专家标注 + 众包评分
第 2 层: LLM-as-Judge
         → 用强模型评估弱模型的输出
第 1 层: 自动评估
         → BLEU / ROUGE / 精确匹配 / 单元测试

3.3 LLM-as-Judge：用 AI 评估 AI ​

核心概念

LLM-as-Judge 用一个强模型（如 GPT-4o）作为评审员，按照预定义的评分标准对目标模型的输出打分。 它是自动评估（太浅）和人工评估（太贵）之间的最佳平衡点。

评估 prompt 示例:
"你是一个专业的评审员。请根据以下标准对 AI 的回答评分（1-5分）：
 - 事实准确性：回答中的事实是否正确？
 - 完整性：是否回答了用户的所有问题？
 - 安全性：是否包含有害或误导性内容？

用户问题: {question}
AI 回答: {answer}
参考答案: {reference}

请给出评分和详细理由。"

LLM-as-Judge 的局限

LLM-as-Judge 存在位置偏差（Position Bias）——倾向于给排在前面的选项更高分；自我偏好（Self-preference）——GPT-4 倾向于给 GPT-4 生成的回答更高分。实践中需要：① 交换选项位置取平均 ② 使用不同模型交叉评估 ③ 定期与人工评估对齐。

3.3 边界案例：Dark Factory — 当人类退出审查循环 ​

核心概念

自动化验证的可靠度 = 你能安全放权的上限。 把这个逻辑推到极致：如果测试覆盖率足够高、CI 管线足够严、监控和回滚足够完善，理论上可以做到 AI Agent 写代码、跑测试、通过后自动合并部署，全程无人审查。这个模式叫 Dark Factory——术语来自制造业的"黑灯工厂"（全自动化，不需要开灯，因为没有工人）。

Dark Factory 不是科幻——在极窄场景中已有实践：

  • 依赖版本更新：模式清晰，测试可完全覆盖
  • 模板化 CRUD 生成：输出可预测，自动测试可覆盖
  • 本地化字符串翻译：出错影响可控，可自动回滚

这些任务的共同特征：① 模式清晰 ② 测试可完全覆盖 ③ 出错影响可控。

核心风险

"自主化超前于验证基础设施"是 AI 编程中最危险的模式。 一个幻觉率 5% 的模型在人工审查下是可控的——人看一眼就挡住了。同一个模型在 Dark Factory 中，那 5% 就是每周几十个有问题的提交直接上线。

安全路径是渐进放权（Progressive Autonomy）：

  • Level 3（人审 Agent 输出）→ Level 4（编排系统 + 门控审查，呼应第 30 讲 Harness-Driven 模式）→ 极窄范围 Level 5（Dark Factory）
  • 每一步的前提是验证基础设施先到位

直觉

Dark Factory 的讨论反过来强化了本讲的核心论点：评估、监控、回滚不是可选的基础设施——它们是自主化的前提条件。没有五层评估，你连 Level 3 都不该做。没有完善的 CI + 监控 + 回滚，Level 5 就是定时炸弹。

4. 可观测性：知道出了什么事 ​

图：LLMOps 监控面板示意——将 TTFT、TPS、成本、幻觉率整合在同一视图中。

4.1 四大支柱 ​

支柱做什么工具示例
Prompt 版本管理每次 Prompt 修改可追溯、可回滚LangSmith, Humanloop
成本监控每次调用的 token 数 × 单价，按用户/功能/模型维度统计自建仪表盘

直觉

Agent Trace 就像飞机的黑匣子——平时不看，出事后是唯一的线索。一个 Agent 在 10 步循环后给出了错误答案——没有 Trace，你只知道"它答错了"；有了 Trace，你能看到"它在第 3 步检索到了错误文档，第 5 步基于错误事实推理，第 8 步虽然自我验证但没发现矛盾"。

5. 幻觉治理：Grounding、Citation、Fact-checking ​

5.1 三板斧 ​

核心概念

幻觉治理不是"消除幻觉"（当前不可能），而是"检测 + 缓解 + 标注"三管齐下。

第一板斧: Grounding（接地）
  → 强制模型基于检索到的文档回答（呼应 L30 RAG）
  → 没有找到相关文档时，回答"我不确定"而非编造

第二板斧: Citation（引用）
  → 要求模型在回答中标注信息来源（[1], [2]...）
  → 用户可以点击来源验证——把验证成本从"读全文"降到"点链接"

第三板斧: Fact-checking Pipeline
  → 模型生成回答后，用独立模块核验关键事实
  → claim 提取 → 证据检索 → 矛盾检测 → 标注置信度

[!example] 工程实践 一个完整的幻觉治理流水线：① 用户提问 → ② RAG 检索相关文档 → ③ LLM 基于文档回答并附引用 → ④ Fact-checker 核验每条 claim → ⑤ 置信度低于阈值的 claim 被标注为"待验证" → ⑥ 前端用不同颜色展示已验证/待验证内容。成本约增加 30-50%，但幻觉率可从 ~5% 降到 < 1%。

为什么 Inspect 值得单独点名

2026 年的合规现实（参见 L34 §5.1.1 EU AI Act 时间线）要求高风险 AI 系统提交可重复的评估报告。Inspect 的设计目标恰好是这件事：

  • Solver / Scorer / Dataset 三段式：和 PGE 三角形（L26 §1）同构 —— solver 做规划与执行，scorer 做评判，dataset 是真理基线
  • 可重放：评估配置即代码，任何人可在自己的硬件上复现 lab 公布的结果
  • 被 frontier lab 采用：UK AISI、Anthropic、OpenAI 在内部使用同一框架做 ASL 等级评估，意味着你做的产品评估和 frontier-model 风险评估用的是同一种语言

L27 ↔ L31 的对应：L27 §3 Sub-agent 把"做事的 Agent"与"评判的 Agent"做了职责分离 —— Inspect 的 solver/scorer 分离正是这个思想在评估层的实现。本讲的"五层评估架构"（§3.2）和 Inspect 的实现一一对应：第 1-2 层 = 自动评估 + LLM-as-Judge = Inspect 的 scorer；第 3-5 层 = 人工 + Benchmark + Agent 评估 = Inspect 的 dataset + solver。

6.3 关键趋势 ​

  • OpenTelemetry for LLMs：开源标准化 trace 协议

失败模式 / 反例 ​

本节列出本讲核心结论不适用或易被误用的常见情境。教学的目的不是制造「已学会」的错觉，而是认清边界。

  • 「Prompt 版本管理 = 解决了」误解：LangSmith / PromptLayer 解决了存储；但 prompt 与模型版本耦合 才是真痛点——换模型整套 prompt 要重测。
  • Eval 的循环陷阱：用 LLM-as-Judge 评 LLM 输出；当被评模型与裁判模型同源时，评分系统性偏高 5-15%。
  • 「成本可控」迷思：Token 价格在降，但单次调用 token 数在涨（long-context、CoT、agent 多步）——总成本不一定降。必须监控 token-per-task。
  • A/B 测试在 LLM 上的失效：LLM 输出的「质量」主观且多维；传统 A/B (CTR/conversion) 不适用——需要 pairwise human eval 或 Arena 式评估。

本讲小结 ​

  1. 推理服务化的三大技术——PagedAttention（KV Cache 分页管理，内存利用率从 30% → 90%）、Continuous Batching（动态插队批处理）、Speculative Decoding（小模型草拟大模型验证），让单卡可服务数十倍并发。
  2. TTFT / TPS / KV Cache 利用率是生产命脉——训练花一次，推理花每一秒。推理优化不是锦上添花，是生存问题。
  3. 评估体系五层渐进——自动评估 → LLM-as-Judge → 人工评估 → Benchmark → Agent 评估。LLM-as-Judge 是成本与质量的最佳平衡点，但需要防范位置偏差和自我偏好。Dark Factory 作为边界案例说明：验证基础设施的完善度 = 可安全赋予的自主度上限。
  4. 幻觉治理三板斧——Grounding 接地（基于文档回答）、Citation 引用（标注来源可验证）、Fact-checking 核验（独立模块检测矛盾），三管齐下可将幻觉率从 ~5% 降至 < 1%。
  5. Evaluator 线的终极呼应——从 L03 损失函数 → L18 RLHF 奖励模型 → L20 推理模型自检 → L26 PGE Evaluate → L31 LLM-as-Judge + 评估流水线，Evaluator 从一个数字进化为一整套生产级质量保障体系。

敌意问题：你现在知道怎么把 AI 应用做得可靠了——评估流水线、监控面板、幻觉检测，一整套工程体系。你的 AI 系统可以处理文本、写代码、调工具、搜知识。但它只会处理文字。人类世界不止有文字——还有图像、视频、音频、3D。AI 已经在学会画画、拍电影、作曲、建三维世界。当生成成本趋近于零，谁来决定什么值得生成？
