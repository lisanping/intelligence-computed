第 23 讲 · Embedding 与向量检索 — AI 的记忆系统 ​

第 11 讲我们种下种子：向量空间是所有模态的通用语言。

11 讲之后，这颗种子结出了工程果实——Embedding 不再只是模型内部的中间表示，而是构建 AI 记忆系统的基础设施。从"一切皆向量"到"一切皆可检索"。

2024-2026 年 向量数据库领域从依附状态走向独立赛道——Pinecone、Weaviate、Qdrant、Milvus、Chroma 都获得了亿美元级别的融资。Embedding 模型从 BERT 年代的辅助角色，变为 Agent 与 RAG 的双引擎。

本讲连接 L11 (向量空间理论) 与 L24 (RAG) / L26 (Agent) / L29 (多模态) 三大应用场景。

前置知识核心产出建议用时
L11（向量空间）、L13（BERT 双向编码）、L22（上下文经济学）① 理解关键词检索与语义检索本质区别 ② 掌握 Bi-Encoder vs Cross-Encoder 架构差异 ③ 掌握 ANN 三大策略（HNSW / IVF / PQ） ④ 掌握 dense + sparse hybrid retrieval ⑤ 掌握 reranker 调优 ⑥ 看 2026 年主流向量数据库生态 ⑦ 拿到 L24 (RAG)、L26 (Agent memory)、L29 (多模态检索) 的伏笔阅读 ~70 分钟 + 动手 ~25 分钟

从上一讲到这一讲 ​

第 22 讲问：上下文窗口装不下全部知识——谁来解决"找得到"？

上一讲你理解了上下文窗口的经济学：每个 token 都有成本，100 万 token 的窗口也装不下 10 亿 token 的知识库。结论很清楚——你需要检索：给定一个问题，从海量文档中找到最相关的几段，只把这几段放进上下文。

但什么是"相关"？关键词匹配太粗糙——用户问"如何提升团队士气"，关键词检索找不到标题是"员工激励方案"的文档。你需要的是语义检索——理解意思，而不是匹配字面。

这就是第 11 讲向量空间呼应线的兑现时刻。

1. 关键词检索 vs 语义检索 ​

1.1 关键词检索：BM25 ​

传统信息检索的代表是 BM25 算法——基于词频（TF）和逆文档频率（IDF）的统计方法：

BM25(q,d)=∑t∈qIDF(t)⋅f(t,d)⋅(k1+1)f(t,d)+k1⋅(1−b+b⋅|d|avgdl)

BM25 很快、很成熟、完全不需要 GPU——但它只看字面重叠。

查询BM25 能找到BM25 找不到
"Python 内存泄漏"包含"Python"和"内存泄漏"的文档标题是"Python gc 模块调优"的文档
"如何提升团队士气"包含"团队"和"士气"的文档标题是"员工激励最佳实践"的文档

1.2 语义检索：Embedding + 向量相似度 ​

语义检索的思路：

  1. 把查询和文档都转成向量（Embedding）
  2. 用余弦相似度或点积找最相近的向量
score(q,d)=eq⋅ed∥eq∥∥ed∥

核心概念

语义检索的本质回到了第 22 讲的核心命题：在向量空间里，相似的东西距离近。 Word2Vec 在词级别实现了这一点；现代 Embedding 模型在句子和段落级别实现了同样的事——"如何提升团队士气"和"员工激励最佳实践"的向量距离很近，即使它们没有共同的关键词。

[!abstract] 呼应线 🔗 向量空间（L11 → L23 呼应 → L29）：第 11 讲建立了"一切皆可嵌入"的概念，当时用 Word2Vec 把词映射到向量空间。本讲把这个概念从"词"扩展到"段落"，从"理解"扩展到"检索"——向量空间不再只是模型内部的中间表示，而是构建 AI 记忆系统的基础设施。

2. Embedding 模型：Bi-Encoder vs Cross-Encoder ​

2.1 Bi-Encoder（双塔模型） ​

Bi-Encoder 独立编码查询和文档，然后用向量相似度打分：

查询 → Encoder → 查询向量 ─┐
                             ├→ cosine similarity → 分数
文档 → Encoder → 文档向量 ─┘

代表模型：Sentence-BERT[1]、OpenAI text-embedding-3-small/large、BGE、GTE。

优点：文档向量可以离线预计算并存储（建索引），查询时只需编码查询 + 向量搜索。百万级文档的检索可以在毫秒级完成。

缺点：查询和文档之间没有交互——Encoder 看不到另一方的信息，表达能力有限。

2.2 Cross-Encoder（交叉编码器） ​

Cross-Encoder 把查询和文档拼接在一起输入一个 Encoder：

[CLS] 查询 [SEP] 文档 [SEP] → Encoder → 分数

优点：查询和文档之间有完整的 Attention 交互，准确率显著高于 Bi-Encoder。

缺点：每个（查询, 文档）对都需要一次完整的前向传播。百万级文档要做百万次推理——完全不可行。

2.3 实际架构：两阶段检索 ​

工业界的标准做法是两阶段流水线：

百万文档 ──[Bi-Encoder 召回 top-100]──→ 100 篇 ──[Cross-Encoder 精排]──→ top-10

直觉

就像找工作：HR 先用"学历 + 关键词"快速筛掉 99% 的简历（Bi-Encoder 召回），然后面试官仔细看剩下的 100 份（Cross-Encoder 精排）。你不可能让面试官读完所有简历，但也不能只靠关键词做最终决定。

3. 相似度度量 ​

三种主流距离度量：

度量公式适用场景
余弦相似度（Cosine）a⋅b|a||b|文本检索（对长度不敏感）
点积（Dot Product）a⋅b推荐系统（向量模长有意义）
欧氏距离（L2）|a−b|2图像特征（绝对距离有意义）

常见误区

选错距离度量会让检索质量崩溃。如果你的 Embedding 模型是用余弦相似度训练的，但你的向量数据库用了 L2 距离——结果会很差。务必确保训练时和检索时使用相同的度量。

4. 向量数据库与 ANN 算法 ​

4.1 暴力搜索的不可行 ​

假设你有 1000 万个 1024 维的文档向量。找到与查询最相似的 top-10 需要计算 1000 万次余弦相似度——每次查询耗时数秒。

近似最近邻（Approximate Nearest Neighbor, ANN） 算法用少量精度损失换取数量级的速度提升：从 O(n) 降到 O(log⁡n) 或更低。

4.2 HNSW（Hierarchical Navigable Small World） ​

HNSW[2] 是目前最流行的 ANN 算法，灵感来自小世界网络（Small World Network）：

  1. 构建阶段：在向量之间建立多层图结构——底层连接多、稀疏层连接少
  2. 搜索阶段：从最顶层开始，在图上"贪心导航"——每一步跳到离目标更近的节点
  3. 逐层下降：在高层快速定位区域，在底层精确搜索

直觉

想象在一个城市找餐厅。HNSW 的策略是：先看全国地图找到正确的城市（顶层），再看城市地图找到正确的街区（中层），最后在街区里逐栋楼找到餐厅（底层）。你不需要遍历全国所有餐厅——只需要在每层做几次"跳转"。

性能：1000 万向量中查 top-10，HNSW 通常只需要访问几千个节点。recall@10 > 95% 时，查询延迟在 1-10 毫秒。

4.3 IVF（Inverted File Index） ​

IVF 先用 K-Means 把向量空间分成 k 个聚类（Voronoi cells），查询时只在最近的 nprobe 个聚类内搜索：

  1. 建索引：对全部向量做 K-Means 聚类
  2. 查询：找到查询向量最近的 nprobe 个聚类中心，只在这些聚类内暴力搜索

速度和精度的权衡由 nprobe 控制：nprobe 越大越准但越慢。

4.4 PQ（Product Quantization，乘积量化） ​

PQ[3] 是一种向量压缩技术——把高维向量分成若干子段，每段独立量化为一个码本索引：

  • 原始：1024 维 × 4 bytes = 4 KB/向量
  • PQ（64 子段 × 8 bits）：64 bytes/向量
  • 压缩比 64 倍

代价是精度损失——但 PQ 常与 HNSW 或 IVF 组合使用（如 IVFPQ），在内存受限场景下非常实用。

4.5 主流向量数据库 ​

数据库类型默认 ANN特点
Pinecone全托管云服务自研开箱即用，按量计费
Weaviate开源HNSW支持混合搜索（向量 + BM25）
Milvus开源多种大规模、分布式、可选 GPU 加速
Qdrant开源HNSWRust 实现，性能好
Chroma开源HNSW轻量级，适合原型开发
FAISS库（非 DB）多种Meta 开源，底层构建块

选型建议

原型阶段用 Chroma（几行代码启动），生产环境根据规模选 Qdrant/Weaviate（百万级）或 Milvus（十亿级）。如果不想运维，用 Pinecone。FAISS 是底层库，适合需要精细控制 ANN 参数的场景。

5. 端到端流程：从文本到可检索的向量 ​

文档 → 分块(Chunking) → Embedding 模型 → 向量 → 向量数据库
                                                       ↓
查询 → Embedding 模型 → 查询向量 → ANN 搜索 → top-K 结果

核心概念

这条流水线就是下一讲 RAG 的前半部分——R（Retrieval）。本讲解决了"怎么找"的问题，下一讲解决"找到了怎么用"的问题。

失败模式 / 反例 ​

本节列出本讲核心结论不适用或易被误用的常见情境。教学的目的不是制造「已学会」的错觉，而是认清边界。

  • 「Embedding 越新越好」误解：text-embedding-3-large 在 MTEB 比 bge-m3 高 2 分，但域外（医疗/法律）上 bge-m3 反超——SOTA 不等于你的 SOTA。
  • Cosine similarity 的陷阱：高维空间下大多数点之间 cosine 在 0.3-0.7 之间；阈值 0.7 看似严格其实召回过宽——必须用业务数据校准。
  • Hybrid retrieval 的真实增益：dense + sparse 在 BEIR 平均提升 5%，但在专有名词、产品 SKU、人名这类查询上提升 30%——这正是工业用 hybrid 的原因。
  • Embedding 模型的版本漂移：换 embedding 模型必须重建整个索引——这是常被低估的运维成本，也是 embedding 模型选择应慎重的根本原因。

本讲小结 ​

  1. 语义检索超越关键词匹配——Embedding 让"意思相近"的查询和文档在向量空间中距离近，解决了词汇不匹配问题。
  2. Bi-Encoder 快但粗，Cross-Encoder 准但慢——工业实践用两阶段流水线：先召回再精排。
  3. ANN 算法是向量检索的核心——HNSW（图导航）、IVF（聚类分区）、PQ（向量压缩）各有适用场景。
  4. 距离度量必须与训练一致——余弦、点积、L2 不可混用，否则检索质量崩溃。
  5. 本讲解决了"找得到"——Embedding + 向量数据库 + ANN 构成了 AI 的记忆系统。下一讲解决"用得好"。

下一讲预告 ​

敌意问题：找到了最相关的文档——谁来解决"用得好"？ 你检索到了 top-10 文档片段，然后呢？直接拼到 Prompt 里就行了吗？如果检索到的内容有矛盾怎么办？如果最相关的片段跨越了两个 chunk 的边界怎么办？如果模型忽略了检索结果、自己编造了答案怎么办？从"检索"到"可靠地利用检索结果生成答案"，中间还有一整条工程流水线要搭。
