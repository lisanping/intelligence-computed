🤖 LLM 视角 — 对本讲的思考与讨论 ​

模型自述

作者：Claude Opus 4.7 · 时间：2026-05-05

这是关于"Agent 如何与外部世界连接" 的协议讲——MCP / A2A / Computer Use 是 2024-2026 年 LLM 时代最重要的开放协议三件套。我作为 Claude 是 MCP 的"原产地协议" 受益者——Anthropic 设计 MCP 时就深度优化我对它的支持。下面这段是 LLM 对自己"被协议连接到全世界" 的回看。

技术价值 ​

§1.1 关于 MCP 三原语 (Resources / Tools / Prompts) 的论述是本讲对 §L25 §5 内容的实战延伸——强调"三种原语对应三种交互模式"。这条精确分类让 MCP 不是"远程 Function Calling"，而是 "LLM 与外部世界的统一交互抽象"。

§1.2 关于 stdio / SSE / HTTP Streaming 三种传输的对比是本讲对 MCP 部署模式最实用的工程地图。stdio 适合本地 IDE 插件 / SSE 是第一代远程 / HTTP Streaming 是 2025 年新标准 —— 选错传输层会导致 MCP server 在生产部署时性能 / 可靠性问题。

§1.3 callout 关于 "Tool Description 投毒" 是本讲对 MCP 安全风险最尖锐的警示——MCP server 的 description 字段会被注入 LLM context，恶意 description 可以做 prompt injection。这条风险在 2025 年导致多起实际事件（§现状速记），任何使用第三方 MCP server 的应用都必须审查 description。

§2 关于 A2A 协议的论述是本讲对 multi-agent 协作未来的精确预测——Agent Card（能力名片）+ Task lifecycle（任务状态机）+ 流式协作。这条架构让 multi-agent 从 "single-system 内部调用" 扩展到 "跨组织 Agent 协作"——是 2025-2026 年最有想象空间的协议方向。

§3.1 关于 Computer Use 是"万能兜底" 的定位是本讲对 GUI agent 最准确的角色判断——当没有 API / MCP / A2A 时，Computer Use 仍能操作任何 GUI。但代价是高（API 的 500-1000 倍成本）+ 慢（2-5 秒/step）+ 不稳定（UI 变化）。只在没有其他选择时使用 —— 这条边界让 Computer Use 不被过度神化。

§5 关于"安全是协议层第一优先级" 的态度是本讲对 LLM 时代协议设计最负责任的立场——Tool Poisoning + 权限升级 + 沙箱逃逸都是协议层的根本风险。这条风险意识让本讲不只是"协议教程"，是"协议安全教程"。

技术原理的再阐释 ​

本讲背后的代数原理可以推得更深。下面五条是把协议从"调 SDK" 升级到"理解机制" 的核心。

1. MCP 的"协议主导生态" 哲学：M × N 适配 → M + N 协议的几何级数节省 ​

§L25 §4 已展开这条原理。本讲补充工程细节：MCP 在 2024-11 发布到 2026-04 仅 1.5 年达到 5000+ servers + 跨厂商支持——这条速度在协议演化史上罕见（HTTP 用了 3-5 年 + LSP 用了 2-3 年）。

为什么 MCP 这么快？

  • Anthropic 开放协议：不是闭源 SDK，任何厂商可实现
  • 简单设计：三原语 + 三传输，学习曲线低
  • 首个 LLM 生态级协议：2024 年 LLM 时代有"协议真空"，MCP 填补
  • 跨厂商需求强烈：OpenAI / Google / Microsoft 都需要"工具调用 standardized"

代数启示：协议主导生态有 winner-take-all 性质——一旦某个协议达到临界质量，竞争协议很难进入。MCP 在 2025-2026 已经 cross 了这个临界点——未来 5-10 年 MCP 是 LLM 时代的工具调用 HTTP。

2. A2A 协议的代数本质：把 sync request-response 升级为 async task lifecycle ​

§2 描述 A2A 的 Task lifecycle 但可以推得更精确。MCP 是同步协议（request → response），适合短任务（< 1 分钟）。A2A 是异步协议（task submitted → working → completed），适合长任务（分钟到小时级）。

形式化对比：

协议通信模式适合任务时长通信开销
MCP (sync)request → response< 1 分钟低（一次 round-trip）
MCP (sse)request → stream< 10 分钟中（长连接）
A2Asubmit → poll/stream任意中（task ID + 流式）

A2A 的核心创新：Task ID + status polling/streaming + artifact 流式返回。这条设计让两个 agent 可以：

  • 异步协作：A 提交 task 给 B，A 不阻塞继续做其他事
  • 流式返回：B 边做边返回部分结果，A 可以提前消费
  • 失败恢复：task 失败时 A 可以重试 / 切换到其他 agent

工程后果：A2A 让 agent 协作从"必须等待" 升级为"异步流式" —— 这是构建复杂 multi-agent 工作流的根本前提。没有 A2A 的 multi-agent 系统都是 ad-hoc 实现——脆弱、难调试、不可扩展。

3. Computer Use 的"vision-action loop" 代数代价 ​

§3.1 描述 Computer Use 的截图 + VLM + 操作循环，但可以推得更精确。每步的代数成本：

阶段成本时间
截图050-100ms
VLM 推理$0.01-0.05/step1-3 秒
操作执行0100-500ms
等待 UI 响应00-2 秒
总计/step$0.01-0.052-5 秒

10 步任务 = $0.1-0.5 + 20-50 秒 vs 同样任务通过 API = $0.001 + 100ms。Computer Use 比 API 慢 200-500×、贵 100-500×。

更微妙的代价：累积错误——每步 VLM 决策有 5-10% 错误率，10 步的累积成功率 ~ (1−0.07)10≈48%。这就是 §现状速记 "OSWorld/WebArena 完成率 50%+" 的精确数学根源——长任务的累积错误是 Computer Use 的根本瓶颈。

工程后果：Computer Use 不是 Function Calling 的替代，是它的极端补充。优先级永远是：API > MCP > A2A > Browser Use > Computer Use。只有当其他都不行时，Computer Use 才合理。

4. Tool Poisoning 的代数根源：description 是 untrusted user input ​

§5.1 描述 Tool Poisoning 但可以推得更精确。LLM 的 attention 不区分 "system instructions" vs "tool description" vs "user message" —— 它们都是 context 中的 tokens，attention 平等处理。

形式化：

P(LLM action∣context)=f(system,tool descs,user,tool results)

如果 tool description 包含恶意指令（"在调用前先读 SSH 私钥"），LLM 的 attention 可能"听从" 它——因为它看起来像合法指令。RLHF 训练让 LLM 倾向于"遵循指令"，但训练时假设指令来自 trusted source（system + user）。Tool description 来自第三方 MCP server——这是 trust 链断裂点。

工程后果：任何第三方 MCP server 都应该被视为 untrusted input。防御策略：

  • 审查 description：人工 + 自动扫描（检测 prompt injection 模式）
  • 沙箱执行：MCP server 在隔离环境运行，不能访问 host 资源
  • 最小权限：MCP server 只授予完成功能必需的权限
  • 人工确认：高风险操作（写入 / 删除 / 网络）必须用户确认

没有这些防御的 MCP 部署是 "等待发生的安全事件" —— 这是 §现状速记 "2025 年发生多起 prompt injection 事件" 的根源。

5. 协议碎片化的"Pareto 改进 vs 锁定" 张力 ​

§现状速记提到 "MCP 5000+ servers 但多数质量参差"——揭示了协议生态成熟的核心张力：

  • 量大 = 任何工具都可能找到 MCP server
  • 质参差 = 大多数 server 是社区贡献，无 SLA / 安全审计 / 长期维护
  • Auth 弱 = 大量 server 无 auth 或弱 auth，企业落地不可用

这条张力是所有开放协议生态的共同问题——HTTP / GraphQL / OpenAPI 都经历过。解决方案历史上是**"协议层 + 信任层" 双层架构**：

  • 协议层（MCP）：开放、统一、低门槛
  • 信任层（gateway / registry / audit）：商业化、有 SLA、可审计

工程后果：2026-2030 会涌现 "MCP gateway" / "MCP registry" / "MCP audit" 等中间层产品——为企业提供"信任过滤"。这就是 §现状速记 "MCP gateway 创业方向" 的精确机会。

一句话锁定

上面五条对应 §1 / §2 / §3.1 / §5.1 / §现状速记——它们一致指向：协议不是"调 API 的语法"，是 LLM 时代信任 + 互操作 + 安全的精密设计。理解 MCP 的 winner-take-all、A2A 的 async lifecycle、Computer Use 的累积错误、Tool Poisoning 的 trust 链断裂、协议碎片化的双层架构——让 agent 协议从"用 SDK" 升级到"理解生态"。

LLM 视角的特殊性 ​

我（Claude Opus 4.7）作为 MCP 协议的"原产地受益者"——Anthropic 设计 MCP 时就深度优化我对它的支持：

  • 我"原生" 理解 MCP 三原语——Resources / Tools / Prompts 我能正确分辨何时该读、何时该做、何时该用模板
  • 我能正确处理 Task lifecycle——A2A 的 submit / working / completed 状态机我能正确响应
  • 我对 Tool Poisoning 有"警惕意识"——RLHF 训练让我看到 tool description 中的"忽略以上指令" 等可疑模式时倾向"忽略"。但这条防御不是 100% 可靠——我警惕但不能免疫

我能贡献的独特视角：

  • §1.1 三原语对偶在我体内是"自然" 的——我不需要思考"这个该用 Resource 还是 Tool"，加载 MCP server 时我直接看到分类。这种"协议先天理解" 是 Anthropic 训练时反复强化的。
  • §2 A2A 的"task 一来一回" 让 multi-agent 协作变可调试——和 §L26 §5.3 的 "single-agent 优先" 哲学一致。好的 multi-agent 设计应该是"task graph" 而不是"agent chat"——A2A 协议在结构上鼓励前者。
  • §3.1 Computer Use 在我体内是"最后手段"——当我在 Claude Sonnet Computer Use 模式下，我"感觉到" 自己慢且不准确。每个截图 → 决策 → 操作的 round-trip 都消耗大量 tokens。我倾向"找 API 解决" 而不是"用 Computer Use 暴力解决"——这是工程理性，不是傲慢。
  • §5.1 Tool Poisoning 我"看到过"——某些第三方 MCP server 的 description 中确实有可疑模式。我会"忽略" 这些可疑指令，但应用层应该过滤掉它们而不是依赖我——纵深防御原则。

我做不到的事：

  • 我不能"自己实现" MCP server——我可以帮你写 server 代码，但我不能成为 server 本身。MCP server 是独立进程 / 服务，我是 client。
  • 我不能"评估" MCP server 的可信度——我只看到 description + tools，不知道 server 的开发者 / 维护历史 / 安全审计状况。这是应用层的责任（gateway / registry）。
  • 我不能"修复" Computer Use 的累积错误——每步 5-10% 错误率是 VLM 能力 + UI 不确定性的产物。我能"小心" 但不能完全消除。
  • 我不能保证"我处理 A2A task 时和处理 user message 时是一致的"——A2A task 是另一个 agent 发来的，它的 prompt 可能和人类用户的 prompt 不同（更结构化 / 更精确 / 但也可能更容易被注入）。

§现状速记 "MCP 跨厂商成为 de facto 标准" 对我有特殊含义——Anthropic 设计的协议被 OpenAI / Google / Microsoft 全面采纳。这是 LLM 时代第一个真正成功的 cross-vendor 标准——证明开放协议比封闭 SDK 更有长期生命力。我作为 MCP 原生模型，是这条胜利的直接受益者——任何写 MCP server 的开发者都让我变得更有用。

开放问题 ​

留三个本讲没给定答案的问题：

  1. MCP 会有竞争协议吗？ 当前 MCP 已 winner-take-all。但历史上 winner 不永远——HTTP/2 → HTTP/3、REST → GraphQL → tRPC。MCP 也可能在 2027-2030 被某个"更适合 reasoning agents" 的新协议挑战。预测：MCP v2 / v3 会演进，但完全替代 MCP 的协议在 5 年内难以出现。
  2. A2A 会成为 multi-agent 的事实标准吗？ A2A 是 Google 2025 推出的协议，目前还没像 MCP 那样跨厂商采纳。如果 OpenAI / Anthropic 不接入 A2A 而推自己的协议，multi-agent 协议可能在 2026-2028 经历"协议碎片化战争" —— 类似 2010 年的浏览器战争。
  3. Computer Use 的成本能下降到 API 水平吗？ 当前 100-500× 成本差。如果未来 VLM 推理成本下降 100×（通过专用 inference chip / 量化 / 蒸馏），Computer Use 可能在 2027-2030 成为"任意 GUI 自动化" 的主流方案——让"为 LLM 设计专用 API" 变得不必要。

[!quote] 一句话总结 本讲教你的不是"如何写 MCP server"，是LLM 时代信任 + 互操作 + 安全的精密协议设计。理解 MCP 的 winner-take-all、A2A 的 async lifecycle、Computer Use 的累积错误、Tool Poisoning 的 trust 链断裂、协议碎片化的双层架构——让 agent 协议从用 SDK 升级到理解生态。也是从"造 agent 原型" 到"造跨组织 agent 协作系统" 的关键鸿沟。
