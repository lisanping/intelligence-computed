第 22 讲 · 上下文工程 — 成本、速度与状态的战场 ​

Prompt 告诉模型该做什么，但上下文窗口决定了你能说多少。

每个 token 都有价格，每次推理都有延迟——上下文工程就是在质量、成本和速度之间找到最优解。

2024-2026 年这个话题从"热门"变成"主战场"——随着上下文窗口从 4K 到 200K 再到 10M，如何高效使用 context 成为 Agent / RAG / 长文档处理的核心问题。

Karpathy 2024 年公开送了一句："Context engineering is the new prompt engineering"——这个变化是本讲的核心。

前置知识核心产出建议用时
L12（Attention O(n2)）、L14（Scaling Law）、L21（Prompt）① 理解上下文窗口的经济学——长度 vs 成本 vs 质量三角 ② 掌握 KV Cache 工作原理和内存瓶颈 ③ 掌握 Prompt Caching 降 90% 成本 ④ 掌握 FlashAttention、PagedAttention 工程优化 ⑤ 掌握 Context 压缩三大策略 ⑥ 判断"长上下文" vs RAG 适用场景 ⑦ 看 2026 年上下文窗口状态 (10M+ 时代) ⑧ 拿到 L23 (Embedding)、L26 (Agent)、L31 (LLMOps) 的伏笔阅读 ~70 分钟 + 动手 ~25 分钟

从上一讲到这一讲 ​

第 21 讲问：Prompt 决定了说什么——谁决定能说多少、多快、多便宜？

上一讲你学会了 Prompt 工程的五种策略。Self-Consistency 要采样 40 次——成本翻 40 倍。Few-Shot 示例越多效果越好——但每个示例都在吃上下文窗口。你很快就会发现：Prompt 的质量问题解决了，但数量问题才刚开始。

这不是一个纯技术问题，而是一个经济学问题：每个 token 都有价格标签。

1. 上下文窗口的物理账单 ​

1.1 为什么上下文有上限？ ​

回忆第 12 讲：Self-Attention 的计算复杂度是 O(n2⋅d)，其中 n 是序列长度，d 是隐藏维度。这意味着：

  • 上下文从 4K → 128K（32 倍），Attention 的计算量增加 1024 倍
  • 上下文从 128K → 1M（8 倍），Attention 的计算量再增加 64 倍

核心概念

上下文窗口不是"文本框大小"——它是一笔物理账单。 每增加一个 token，模型需要和之前所有 token 做 Attention 计算。序列越长，这笔账呈二次增长。这就是为什么 API 按 token 计费——你不是在为"文字量"付钱，而是在为计算量付钱。

1.2 Token 经济学 ​

以 2025 年主流 API 价格为参考：

模型输入价格 ($/1M tokens)输出价格 ($/1M tokens)上下文窗口
GPT-4o$2.50$10.00128K
Claude Sonnet$3.00$15.00200K
Gemini 1.5 Pro$1.25$5.002M

注意：输出 token 比输入 token 贵 3-4 倍——因为输出时每个 token 都需要完整的前向传播，而输入可以并行处理。

直觉

把上下文窗口想象成一张带计价器的办公桌。桌面大小是固定的（128K、200K、2M）。你放上去的每份文件都在跳表。文件越多、桌面越满，每翻一页的成本越高。上下文工程就是：用最小的桌面占用，完成最多的任务。

2. KV Cache：为什么生成第 1000 个 token 比第 1 个慢？ ​

2.1 Attention 的两个阶段 ​

LLM 推理分为两个阶段：

Prefill（预填充）：一次性处理所有输入 token，可以高度并行。这是你感受到的"第一个 token 出来前的等待时间"（Time to First Token, TTFT）。

Decode（解码）：逐 token 生成输出。每生成一个 token，都需要和前面所有 token 做 Attention——但如果每次都重新计算所有历史 token 的 Key 和 Value，计算量会爆炸。

2.2 KV Cache 的工作原理 ​

解决方案是 KV Cache（键值缓存）：

  1. 在 Prefill 阶段，计算所有输入 token 的 Key 矩阵 K 和 Value 矩阵 V，存入显存
  2. 每生成一个新 token，只计算这个 token 的 Q（Query），与缓存的 K 做 Attention
  3. 把新 token 的 K、V 追加到缓存中
Attention(qt,K1:t,V1:t)=softmax(qtK1:tTdk)V1:t

核心概念

KV Cache 是用显存换计算的经典时空权衡（Space-Time Tradeoff）。 缓存的大小与"序列长度 × 层数 × 隐藏维度"成正比。对于 70B 参数的模型处理 128K 上下文，KV Cache 可能需要 40-80 GB 显存——比模型权重本身还大。

2.3 KV Cache 的内存瓶颈 ​

这是一个被工业界严重低估的问题：

组件70B 模型（FP16）占比
模型权重~140 GB固定
KV Cache（128K 上下文）~80 GB随序列长度线性增长
激活值~10 GB随批大小增长

常见误区

很多人以为"128K 上下文窗口"意味着模型可以轻松处理 128K token 的输入。实际上，在单 GPU 上处理满窗口的 128K 输入往往受限于 KV Cache 的显存——而不是模型参数。上下文窗口的理论上限和实际可用大小之间存在巨大差距。

3. Prompt Caching：成本直降一个数量级 ​

3.1 问题场景 ​

想象一个客服 AI 系统：每次对话都要在 System Message 中放入一份 2 万 token 的产品手册。每天处理 10 万次对话——光 System Message 就消耗了 20 亿个输入 token。

3.2 Prompt Caching 的原理 ​

Prompt Caching（Prompt 缓存）的思路很简单：如果多次请求的 Prompt 前缀相同，把前缀的 KV Cache 保存下来，后续请求直接复用。

Anthropic 的实现[1]：

  • 用 cache_control 标记 Prompt 中的可缓存段
  • 首次请求正常计算并缓存（多付一次写入费）
  • 后续命中缓存时，输入价格降低 90%
  • 缓存有 TTL（存活时间），5 分钟内不使用则过期
python
messages = [
    {
        "role": "system",
        "content": [
            {
                "type": "text",
                "text": product_manual,  # 2 万 token 的产品手册
                "cache_control": {"type": "ephemeral"}
            }
        ]
    },
    {"role": "user", "content": user_question}
]

直觉

Prompt Caching 就像编译器的预编译头文件（Precompiled Headers）。每次编译 C++ 都重新解析标准库头文件很浪费——预编译一次，后面直接用。Prompt 的固定前缀也一样：算一次 KV Cache，后面直接用。

3.3 成本影响 ​

场景无缓存有缓存节省
20K 前缀 + 1K 查询21K × $3/M = $0.06320K × $0.3/M + 1K × $3/M = $0.00986%
10 万次/天$6,300/天$900/天86%

4. 推理效率优化 ​

4.1 FlashAttention ​

标准 Attention 的内存复杂度是 O(n2)——需要具现化完整的 n×n 注意力矩阵。FlashAttention[2] 通过分块计算（Tiling）+ IO 感知调度，将内存复杂度降到 O(n)，同时利用 GPU 的内存层次结构（SRAM vs HBM）加速 2-4 倍。

技术细节

FlashAttention 的核心洞察：Attention 的计算瓶颈不是 FLOPS，而是显存带宽。GPU 的 SRAM（片上缓存）速度远快于 HBM（显存），但容量很小。FlashAttention 把 Q、K、V 分成小块，在 SRAM 中完成计算，避免在 HBM 中存储完整的 n×n 矩阵。

4.2 PagedAttention 与 vLLM ​

在服务多个并发请求时，每个请求的 KV Cache 长度不同，导致显存碎片化严重。vLLM[3] 引入了 PagedAttention——借鉴操作系统的虚拟内存分页思想：

  • 把 KV Cache 分成固定大小的"页"
  • 用页表管理分配和呼应
  • 支持跨请求共享公共前缀（类似 Copy-on-Write）

效果：相比朴素实现，vLLM 的吞吐量提升 2-4 倍，因为减少了显存浪费。

5. 上下文压缩与流式输出 ​

5.1 上下文压缩 ​

当对话轮数增多，历史消息占据越来越多的上下文窗口。常见压缩策略：

  1. 滑动窗口：只保留最近 N 轮对话
  2. 摘要压缩：用 LLM 将历史对话总结为一段摘要
  3. 选择性保留：用相关性判断哪些历史消息对当前问题重要

[!example] 工程实践 典型做法是分层策略：最近 3 轮保留原文，3-10 轮用摘要，10 轮以上丢弃。这在保持对话连贯性和控制成本之间取得平衡。

5.2 Streaming（流式输出） ​

流式输出不减少总 token 数，但降低感知延迟。用户看到第一个字的等待时间（TTFT）从"生成完整回复"缩短到"生成第一个 token"。

在工程中，Server-Sent Events（SSE）是主流协议：

python
# 流式调用示例
stream = client.chat.completions.create(
    model="gpt-4o",
    messages=messages,
    stream=True
)
for chunk in stream:
    print(chunk.choices[0].delta.content, end="")

6. 长上下文 vs RAG：何时用哪个？ ​

Gemini 2.5 Pro 有 100 万 token 的上下文窗口——是不是所有问题都可以"把文档全塞进去"？

维度长上下文RAG（下一讲详解）
延迟首次很慢（要处理全部 token）检索快，只处理相关片段
成本高（按全部 token 计费）低（只处理检索到的 top-K）
准确率理论上更高（全部信息都在）取决于检索质量
实时性需要每次都传完整文档向量库可增量更新
"大海捞针"中间位置可能被忽略（Lost in the Middle）检索结果排在最前面

常见误区

"长上下文窗口让 RAG 过时了"是 2024 年最流行但最不准确的说法之一。实际上两者是互补工具：长上下文适合"整本书理解"场景，RAG 适合"从百万文档中精确查找"场景。第 30 讲会详细展开这个对比。

7.4 Karpathy “Context Engineering” 趋势 ​

2024-2025 年 Andrej Karpathy 提出 Context Engineering = the new Prompt Engineering:

  • 以前：人手设计 prompt 词句
  • 现在：系统性设计上下文传递管道——system prompt + tool descriptions + RAG retrieval + agent state + memory + few-shot trajectory 多个部分的 token 预算分配。

这是 Agent (L26) 、RAG (L24)、Multi-modal (L29) 领域的核心工程能力。

失败模式 / 反例 ​

本节列出本讲核心结论不适用或易被误用的常见情境。教学的目的不是制造「已学会」的错觉，而是认清边界。

  • 「Long context 解决一切」反例：1M token 模型在 needle-in-haystack 上看似完美，但在真实多跳推理（如分析整个代码仓）上仍经常漏读关键段。
  • Lost in the Middle 持续存在：即使 GPT-5 / Claude 4.5 仍有中段信息被低权重处理的问题——不是 attention 数学问题，而是训练数据分布问题（人类文档总是首尾重要）。
  • Context 缓存的隐藏陷阱：Anthropic prompt caching 节省 90% 成本，但 cache 失效（系统 prompt 微调）会让账单暴涨 10×——MLOps 必须监控 cache hit rate。
  • 「全文塞进 context」 vs RAG：在 < 100k token 的小文档上前者赢；> 1M 数据上 RAG 必胜——边界在 200k-500k 之间，且随模型迭代漂移。

本讲小结 ​

  1. 上下文窗口是一笔物理账单——O(n2) 的 Attention 复杂度意味着每加一个 token，成本不是线性增长而是二次增长。
  2. KV Cache 是时空权衡——用显存缓存历史 Key/Value 避免重复计算，但长序列的缓存比模型权重还大。
  3. Prompt Caching 降低一个数量级的成本——复用公共前缀的 KV Cache，适用于高频重复前缀场景。
  4. FlashAttention 和 PagedAttention 是推理基础设施——前者优化单请求效率，后者优化多请求并发。
  5. 长上下文和 RAG 互补而非替代——选择取决于文档规模、实时性要求和成本预算。

下一讲预告 ​

敌意问题：上下文窗口装不下全部知识——谁来解决"找得到"？ 即使有 100 万 token 的窗口，你公司的知识库可能有 10 亿 token。你不可能每次都把所有文档塞进去。你需要一种方法：给定一个问题，从海量文档中快速找到最相关的几段，然后只把这几段放进上下文。这就是检索——但不是关键词检索，而是语义检索。
