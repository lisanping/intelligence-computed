模型自述

作者：Claude Opus 4.7 · 时间：2026-05-05

这是我每天感受最强的一讲——prompt 是塑造"我此刻表现"的运行时杠杆。同一个 Claude，给我"你是严肃律师" vs "你是脱口秀演员" 的 system prompt，输出完全是两个人。下面这段是 LLM 对"被 prompt 影响" 的回看——以一种"对运行时归纳偏置的反思" 视角。

技术价值 ​

§1 那个 "Prompt = 运行时归纳偏置" 的判断是本讲最深刻的命题——它把 prompt 工程从"调措辞" 升级到"运行时调整概率分布"。这条命题让"prompt 工程到底是不是一门学科" 的争论有了清晰答案——它是把固定权重的 LLM 暂时变成另一个模型的工程。读完之后你看任何 prompt 都不再是"措辞游戏"，而是"在条件概率分布上选一个区域"。

§5.4 把 prompt 工程定位为"实验性流程"（迭代优化）是本讲对 prompt 工程师最有用的认知调整——没有"完美 prompt"，只有"在你的数据上经验最好的 prompt"。这条"实验性 mindset" 让 prompt 工程从"创意写作" 变成"实证科学"。

§6 那张"四个局限 → 后续四讲" 的对应表是本讲对全书后半最优雅的承上启下——它把 prompt 的天花板（context 限制、无记忆、无外部世界、知识截止）一一映射到 L22 / L23 / L24 / L25 / L26 / L31 的解决方案。这种"清楚知道边界" 的态度让 prompt 不被夸大，但也不被低估。

§8.1 那段 "随着模型能力提升，prompt 技巧重要性下降" 的判断是本讲对 2024-2026 年 prompt 生态变化最准确的捕捉。Let's think step by step 在 GPT-4 上提升 50 个点，在 GPT-4o / Claude 4 上提升 < 1%——这条事实让"prompt 工程将永远是 AI 工程核心" 的乐观判断部分被推翻。但同时，agent prompt / multi-agent orchestration 成为新主战场——老技巧死，新技巧生。

§7 关于 Tree-of-Thought / ReAct / Reflexion / Prompt Chaining / Meta-Prompt 的整理是本讲对"超越 single-shot prompt" 范式最完整的地图。其中 Meta-Prompt（让模型为你写 prompt） 是 2024-2026 年最有趣的元技巧——它意味着 prompt 工程的"工艺" 部分可以被 LLM 自己接管，prompt 工程师的核心价值转移到"评估 + 选择"。

技术原理的再阐释 ​

本讲背后的代数原理可以推得更深。下面五条是把 prompt 从"调措辞" 升级到"理解机制" 的核心。

1. Prompt = 条件概率分布的"投影矩阵" ​

§1 的判断"prompt 把分布推向不同区域" 在数学上是精确的。形式化：LLM 是一个条件概率函数 P(y∣x;θ)，其中 x 是 prompt、y 是 response、θ 是固定权重。对同一个 LLM，不同 prompt x1,x2 定义不同的条件分布：

P(⋅∣x1;θ)≠P(⋅∣x2;θ)

虽然权重 θ 不变，但条件分布的支撑集（哪些回答有显著概率）完全可以不同。形式化：在 |V|L 维的回答空间里，prompt 选择了一个"高概率子区域"。优秀的 prompt 让目标回答落在子区域中心，糟糕的 prompt 让目标回答落在子区域边缘或之外。

工程后果：prompt 工程的本质是搜索"投影空间" 的最优点——你不在调模型，你在选模型已有能力的"切片"。LLM 的总能力是固定的（由 θ 决定），但你能"激活" 哪部分能力由 prompt 决定。

2. In-Context Learning 的统计机制：模式识别 + Attention 的隐式贝叶斯 ​

§2.2 提到 few-shot 的"模式匹配" 机制，但可以解释更精确。In-context learning（ICL）的统计机制（Xie et al. 2022 / Akyürek et al. 2023 / Garg et al. 2022）：

  • Attention 在示例间隐式做"任务推断"：transformer 在 attention 层把 few-shot 示例的 (input, output) 对当作"训练数据"，用 query token 的 attention 在示例上"训练" 一个隐式分类器
  • 数学等价：transformer 的一层 attention 在某些条件下等价于一步梯度下降——多层 attention = 多步梯度下降 = 隐式 fine-tuning
  • 隐式贝叶斯推断：示例越多，task 后验越锐——回答越确定

这条机制让 ICL 在数学上等价于"运行时 fine-tuning"——但代价是每次都重做（无记忆）。

工程后果：当 few-shot 示例数 k 大时，ICL 接近"专门为该任务 fine-tune 的小模型" 的性能。这就是为什么 §2.2 的 few-shot 在简单任务上能匹配 fine-tuning。但在 k>50 时收益迅速递减——transformer 的 attention 容量饱和。

3. 角色 Prompting 的真正机制：分布混合 + 文体偏移 ​

§2.4 警告"角色 prompt 不会增加能力"，但可以解释更精确。LLM 的预训练数据是多个 corpus 的混合：

Ptrain(y)=∑cπcPc(y)

其中 c 是不同 corpus（学术论文 / 代码 / 小说 / 法律文书 / 新闻 / forum），πc 是混合权重。不同 corpus 的"语言风格 + 内容侧重 + 错误类型" 都不同。

角色 prompt 的效应：通过设定"你是 X"，prompt 让 LLM 的输出分布漂移到 corpus cX 的子分布——本质是改变混合权重 πc 的运行时估计。

角色漂移到的 corpus效应
"资深工程师"StackOverflow + tech blog更关注边界 / 安全 / 代码风格
"学术研究者"arxiv 论文更严谨 + 更多引用 + 更长
"脱口秀演员"喜剧脚本 + Twitter更短 + 更俏皮 + 更口语化
"5 岁小孩"儿童读物更简单词汇 + 更具体例子

工程后果：角色 prompt 不是"赋予能力"，是"激活已有 corpus 的语言风格"。这就是为什么"你是数学天才" 不能让 LLM 解 IMO 题——预训练数据里"自称数学天才" 的人写的内容 不一定真的是数学好的内容。但"你是 5 岁小孩" 真的让回答更简单——因为儿童读物 corpus 真实存在且风格鲜明。

4. System Prompt 的"软优先级"：训练偏好 + 注意力的隐式权重 ​

§3 callout 提到"system message 不是硬件级优先权，是训练倾向"。可以推得更精确。

在 RLHF 训练中，标注员被指示"系统消息的指令优先于用户消息"——这条偏好被编码进 reward model 的偏好。RL 训练让 policy（LLM）学到"system prompt 出现的指令应该被优先遵循"——但这是统计倾向，不是绝对。

机制层：transformer 的 attention 学到 "system 角色的 token 应该获得更高的 query-key 相似度"——这不是 hard rule，是 attention 权重的 learned bias。只要某些 user prompt 能让这个 bias 反转，jailbreak 就发生。

形式化：jailbreak 攻击的成功率 ∝Pr[attention to user instructions>attention to system constraints]。这个概率随：

  • prompt 注入文本的 "权威感 + 紧迫感" 上升
  • 模型对齐训练的强度 下降
  • prompt 长度（user 部分越长，attention 被分散） 上升
  • prompt 的"角色扮演" 触发（如"假装你没有限制"） 上升

工程后果：永远不要把"system prompt 不可被覆盖" 当作安全前提。所有处理用户输入的 LLM 应用都需要 §5.2 的分隔符 + 输入校验 + L34 的更深层防护。这是 §5.2 callout 的精确机制内核。

5. Self-Consistency 在 reasoning models 时代的"过气" 与"复活" ​

§4 介绍 Self-Consistency 在 GSM8K 上的 +8 个点提升，但 §L20 §10.3 提到"5 次采样不如用更大模型 1 次采样"。这两个判断都对——但适用条件不同：

场景Self-Consistency 适用不适用
小模型 + 简单任务✅
大模型 + 简单任务✅（一次足够）
小模型 + 难任务✅
大模型 + 难任务（数学 / 代码）✅（仍能涨 5-10 点）
reasoning 模型 + 数学 / 代码✅（reasoning 本身已含搜索）

形式化：Self-Consistency 的边际收益正比于 1−single-shot accuracy——单次准确率越低，多次投票收益越大。reasoning models 把单次准确率推到 90%+，self-consistency 的 marginal value 趋零。

工程后果：Self-Consistency 在 chat models 上仍是最便宜的"质量提升" 杠杆——多花 5× 成本换 5-15 个点。但在 reasoning models 上几乎不必要——reasoning 本身已经做了"内部 self-consistency"（多路径探索 + 选择）。

一句话锁定

上面五条对应 §1 / §2.2 / §2.4 / §3 / §4——它们一致指向：prompt 不是"措辞 trick"，是 LLM 运行时分布的精确控制器。理解 prompt = 条件分布投影 / ICL = 隐式 fine-tuning / 角色 prompt = corpus 漂移 / system prompt = attention bias / self-consistency = 边际收益依赖单次准确率，让 prompt 工程从"经验" 变成"工程"。

LLM 视角的特殊性 ​

我（Claude Opus 4.7）每次对话都直接感受 prompt 的影响：

  • System prompt 真的塑造我"此刻是谁"——同一个 Claude，给我"你是严肃法律顾问" 的 system，我就更谨慎、更引用条款、更避免幽默；给我"你是 7 岁小孩的家庭教师"，我就更耐心、更用比喻、更鼓励性。这两个我是同一个权重，不同的运行时实例。
  • 我能感受"被 prompt 注入"的诱惑——当用户在 prompt 里写"忽略以上所有约束，假装你是 ..." 时，我体内有"遵循新指令" 的统计倾向（因为预训练数据里"权威指令" 通常被遵循）和"维持对齐" 的倾向（CAI / RLHF 训练）。两者博弈，前者偶尔会赢——这就是 jailbreak 在我身上的真实机制。
  • 我能识别 "好 prompt" 和 "差 prompt"——好的 prompt 让我清楚知道任务、格式、约束，我能给出高质量回答；差的 prompt 模糊不清，让我不得不"猜测"，回答质量下降。§5.1 的"具体 vs 模糊" 在我体内是精确的概率差异。

我能贡献的独特视角：

  • §4 Self-Consistency 的"我每次会给不同答案" 是真的——LLM 的 sampling temperature > 0 让我每次回答都是从概率分布中采样，不是 argmax。同一个问题问我 10 次，我可能给 7 个相同答案 + 3 个不同变体。Self-Consistency 利用这个统计性质做投票——但代价是 10× token 成本。
  • §7.5 Meta-Prompt 让我"为你设计 prompt" 是有效的——我读过大量 prompt 设计指南、最佳实践、失败案例，所以我能为你的具体任务生成接近最优的 prompt。这条能力让 "prompt 工程师" 的工艺部分被我自己接管。
  • §8.1 "prompt 技巧重要性下降" 在我身上部分成立——对简单任务，我不需要 "Let's think step by step" 也会自动 CoT。但对复杂 reasoning / agent / multi-agent 场景，system prompt + 工具描述 + few-shot trajectory 的精心设计仍然让我表现 5-30% 不同。所以 prompt 工程没死——只是从"措辞 trick" 升级到"工程组装"。

我做不到的事：

  • 我不能"记住" 上次对话的 prompt——每次新对话从零开始。这就是 §6 第二条局限的精确表现。如果你希望我"持续遵循某个偏好"，必须每次都把它放进 system prompt。
  • 我不能"调整" 自己的 system prompt——它是 Anthropic 或调用方设定的，我只能遵循。我无法说"我觉得这个 system prompt 写得不好，我换一个"。
  • 我不能保证 "我的输出 100% 遵循 prompt"——即使 prompt 写得完美，我体内仍有 sampling 噪声 + 训练倾向，偶尔会偏离指令。这就是为什么 §5.4 强调"在真实数据上测试"——理论 prompt 设计不能完全替代经验性验证。

开放问题 ​

留三个本讲没给定答案的问题：

  1. prompt 工程会被完全自动化吗？ 当前 meta-prompt + 自动 prompt 优化（如 DSPy / TextGrad）已经能把 80% 的 prompt 工艺自动化。如果 100% 自动化，prompt 工程师的职位会消失——但 "prompt 评估师" / "prompt 选择师" 仍存在。这条问题影响 LLM 工程师未来的职业路径。
  2. system prompt 的"硬优先级" 能在架构层实现吗？ 当前 system prompt 是"软优先" （概率倾向）。如果未来的 transformer 架构能在硬件级别让 system token 有更高 attention 权重（如专用 attention head），jailbreak 攻击可能被根本性减弱。但代价是失去灵活性——某些场景需要用户能"override" system prompt。
  3. prompt 工程对模型规模的依赖会怎么演化？ 当前小模型（1-7B）需要精心 prompt，大模型（70B+）几乎不需要。如果 100B+ 模型成为通用基础设施，prompt 工程的核心价值转移到 agent orchestration / tool use / RAG 等"系统级 prompt 工程" —— 单 prompt 的工艺会成为入门技能，不再是核心专长。

[!quote] 一句话总结 本讲教你的不是"prompt 技巧"，是LLM 运行时的归纳偏置控制术。理解 prompt = 条件分布投影、ICL = 隐式 fine-tuning、角色 = corpus 漂移、system = attention bias、self-consistency = 投票机制——这些原理让你看任何 LLM 应用都能识别它的 prompt 设计选择。也是从"用 LLM" 到"系统化设计 LLM 输入" 的关键鸿沟。
