第 24 讲 · RAG — 让 AI 拥有你的知识 ​

检索解决了"找得到"，但从"找到文档"到"可靠地利用文档生成答案"，中间是一整条工程流水线。

RAG (Retrieval-Augmented Generation — 检索增强生成) 是 2024-2026 年 AI 应用最主流的架构模式——它让模型不再只靠"记忆"，而是可以"查资料再回答"。

这一讲是 LLM 应用从"玩具"走向"生产"的必经之路。不理解 RAG 的 6 阶段流水线 + 三代架构演进，你会在生产环境上狠狠撞墙。

2024-2026 年全球企业上获 LLM 部署中超过 60% 与 RAG 有关——这是独立开发者 / 中小企业调 LLM 能力的首选路y径。

前置知识核心产出建议用时
L21（Prompt）、L22（Context）、L23（Embedding）① 理解 RAG 6 阶段流水线架构 ② 掌握分块 (Chunking) 策略工程权衡 ③ 理解混合检索、重排序、HyDE 等高级技术 ④ 区分 Naive / Advanced / Modular RAG 三代架构 ⑤ 掌握 RAG 评估（RAGAS） ⑥ 判断 RAG vs 微调适用场景 ⑦ 看 2026 年 RAG 生态 (LangChain / LlamaIndex / DSPy) ⑧ 掌握 GraphRAG / Agentic RAG 些新趋势 ⑨ 拿到 L25 (Function Calling)、L26 (Agent)、L31 (LLMOps) 的伏笔阅读 ~75 分钟 + 动手 ~25 分钟

从上一讲到这一讲 ​

第 23 讲问：找到了最相关的文档——谁来解决"用得好"？

上一讲你搭建了 AI 的记忆系统：Embedding 模型把文本变成向量，向量数据库用 ANN 算法在毫秒级找到 top-K 相关文档。但"检索到"只是第一步——你直接把 10 段文档片段拼进 Prompt，模型可能：

  • 忽略检索结果，用自己的"记忆"编造答案（幻觉）
  • 被噪声干扰，检索结果中混入了不相关内容
  • 跨 chunk 断裂，答案恰好被切在了两个 chunk 的边界上

RAG 的完整流水线就是为了系统性地解决这些问题。

1. RAG 的起源与核心思想 ​

2020 年，Lewis 等人发表了 RAG 的奠基论文[1]：

核心概念

RAG = Retrieval + Generation。 核心思想极其简单：先检索，再生成。不让模型凭记忆回答，而是先从外部知识库中找到相关信息，把它作为上下文喂给模型，让模型基于这些信息生成答案。

为什么不直接微调模型？

维度微调（Fine-tuning）RAG
知识更新需要重新训练更新知识库即可（分钟级）
成本GPU 训练成本高向量数据库 + API 调用
可溯源不知道答案从哪来可以返回检索到的原文引用
幻觉控制困难（知识编码在参数中）相对容易（答案有据可查）
适用场景风格/格式/领域能力的深度适配需要精确事实、实时信息的问答

直觉

微调像背书——把知识编码进大脑（参数），考试时从记忆中提取。RAG 像开卷考试——允许翻书（检索），考的是"快速找到相关内容 + 正确理解并使用它"的能力。两者不互斥：你可以微调一个擅长"开卷考试"的模型。

2. RAG 六阶段流水线 ​

一个完整的 RAG 系统包含六个阶段：

① 文档加载 → ② 分块 → ③ 索引 → ④ 检索 → ⑤ 增强 → ⑥ 生成
   (Load)    (Chunk)  (Index)  (Retrieve) (Augment) (Generate)

阶段 ①：文档加载（Load） ​

从各种来源提取纯文本：PDF、Word、HTML、Markdown、数据库、API。

常见误区

文档加载看似简单，实际上是 RAG 系统中最容易出错的环节。PDF 的表格解析、扫描件的 OCR、HTML 的噪声清洗——任何一步出问题，后续所有环节的质量都会崩溃。"Garbage in, garbage out"在 RAG 中特别致命。

阶段 ②：分块（Chunking） ​

这是 RAG 工程中最关键的决策之一。

3. 分块策略 ​

3.1 为什么要分块？ ​

Embedding 模型通常有输入长度限制（512-8192 tokens）。即使没有限制，把整篇文档编码成一个向量会稀释语义信号——一个 10 万字文档的单一向量无法精确匹配一个具体问题。

3.2 四种分块策略 ​

策略方法优点缺点
固定大小每 500 token 切一刀简单、可预测可能切断语义单元
重叠窗口每 500 token 切一刀，前后重叠 50 token减少边界信息丢失冗余存储
语义分块（Semantic Chunking）根据句间相似度的变化点分块语义完整计算开销大
结构化分块按文档结构（章节、段落、Markdown 标题）分块尊重文档结构依赖文档格式规范

直觉

分块就像切面包：切太厚（chunk 太大），嘴放不下（超出 Embedding 模型限制），味道混在一起（语义稀释）；切太薄（chunk 太小），碎成渣（缺少上下文），夹不住东西（信息不完整）。最佳厚度取决于你要做什么三明治（查询类型）。

3.3 工程建议 ​

python
# 推荐的起始配置
chunk_size = 512      # tokens
chunk_overlap = 50    # tokens

[!example] 工程实践 实际项目中的分块策略往往是混合的：对 Markdown 文档按标题分块，对 PDF 先按段落分块再合并到目标大小，对代码文件按函数/类分块。没有万能的分块策略——只有适合你数据的分块策略。

3.4 Late Chunking：2024 年的反直觉发现 ​

核心概念

Late Chunking（延后分块）[2]：传统分块在 Embedding 之前切分文档，每个 chunk 独立编码，丢失全局上下文。Late Chunking 反过来：先把整篇文档过一遍长上下文 Embedding 模型，再在 token-level embedding 序列上做分块，每个 chunk 的向量都"知道"它在全文中的位置。

text
传统分块（Naive Chunking）：
  document ─切─→ chunk₁ ─embed─→ vec₁
                 chunk₂ ─embed─→ vec₂   ← 每个 vec 对其它 chunk 一无所知
                 chunk₃ ─embed─→ vec₃

Late Chunking：
  document ─embed (long ctx)─→ token_embs[1..N]
                              ─切─→ vec₁ (= mean-pool token_embs[1..k₁])
                                    vec₂ (= mean-pool token_embs[k₁..k₂])  ← 每个 vec 编码了全文上下文
                                    vec₃ (= mean-pool token_embs[k₂..k₃])

实验结果（Jina v3 在 LongBench 上）：在长文档（> 4K tokens）上 Recall@10 提升 5–15%，对短文档无显著影响。

适用边界

Late Chunking 不是免费的午餐：

  • 必需支持长上下文（≥ 8K tokens）的 Embedding 模型（Jina v3、Voyage 3、Cohere Embed v4 都支持）
  • 编码成本与文档长度成线性，比 Naive Chunking 略贵
  • 在短文档（< 1K tokens）和高度结构化文档（如 FAQ）上收益接近零

决策建议：长篇技术文档、法律合同、学术论文 → 优先 Late Chunking；短文本 / 强结构文档 → Naive Chunking 已足够。

4. 混合检索与重排序 ​

4.1 混合检索（Hybrid Search） ​

纯语义检索可能遗漏包含精确关键词的文档；纯关键词检索不理解语义。混合检索结合两者：

scorehybrid=α⋅scoresemantic+(1−α)⋅scoreBM25

Weaviate、Qdrant 等向量数据库原生支持混合检索。通常 α=0.5∼0.7 是好的起点。

核心概念

混合检索是 2024-2025 年 RAG 工程的默认配置。它解决了一个具体问题：当用户的查询同时包含精确名词（公司名、产品编号）和模糊意图时，纯语义或纯关键词检索都不够好。

4.2 重排序（Reranking） ​

上一讲提到的两阶段检索在 RAG 中的应用：

  1. 第一阶段：Bi-Encoder + BM25 混合检索，召回 top-50
  2. 第二阶段：Cross-Encoder 对 50 个候选精排，输出 top-5

重排序可以显著提升最终答案的质量——因为生成模型只看到 top-5，如果 top-5 的质量差，再好的生成模型也救不回来。

5. Naive RAG → Advanced RAG → Modular RAG ​

5.1 Naive RAG ​

最基本的 RAG：检索 → 拼接 → 生成。

python
# Naive RAG 伪代码
chunks = retrieve(query, top_k=5)
context = "\n".join(chunks)
prompt = f"基于以下内容回答问题：\n{context}\n\n问题：{query}"
answer = llm(prompt)

Naive RAG 的问题：检索质量不稳定、没有去噪、容易幻觉、无法处理多轮对话。

5.2 Advanced RAG ​

在 Naive RAG 基础上加入优化[3]：

检索前（Pre-Retrieval）：

  • 查询改写（Query Rewriting）：用 LLM 把用户模糊的问题改写成更适合检索的形式
  • 查询扩展（Query Expansion）：生成多个变体查询，合并检索结果
  • HyDE（Hypothetical Document Embeddings）：让 LLM 先生成一个"假想答案"，用它做检索

检索后（Post-Retrieval）：

  • 重排序（Reranking）
  • 上下文压缩：去除检索结果中与问题无关的部分
  • 去重与融合

技术细节

HyDE 的直觉很巧妙：用户问"什么是光合作用"，LLM 先编一段"光合作用是植物利用阳光..."（可能不准确），然后用这段假想答案的向量去检索——因为答案和答案之间的语义距离，往往比问题和答案之间的距离更近。

5.3 Modular RAG ​

2024 年以来，RAG 架构从"线性流水线"演进为模块化：每个组件可以独立替换和组合。

┌─────────────────────────────────────────────┐
│  路由（Router）：判断是否需要检索            │
├─────────────────────────────────────────────┤
│  检索模块：向量 / BM25 / 知识图谱 / SQL     │
├─────────────────────────────────────────────┤
│  后处理：重排 / 压缩 / 融合                  │
├─────────────────────────────────────────────┤
│  生成模块：LLM + 带引用的输出格式            │
├─────────────────────────────────────────────┤
│  自检模块：检测幻觉、验证答案与来源一致性    │
└─────────────────────────────────────────────┘

核心变化：不是所有查询都需要检索。路由模块先判断——简单问题（"1+1=?"）直接回答，事实性问题才触发检索。

6. RAG 评估 ​

6.1 三个核心指标 ​

RAG 系统的评估需要同时考量检索质量和生成质量：

指标衡量什么方法
忠实度（Faithfulness）生成的答案是否忠于检索到的内容LLM-as-Judge 检查事实一致性
答案相关性（Answer Relevance）生成的答案是否回答了用户的问题LLM-as-Judge 评估相关度
上下文相关性（Context Relevance）检索到的内容是否与问题相关计算检索结果中相关片段的比例

6.2 RAGAS 框架 ​

RAGAS[4] 是目前最流行的 RAG 评估框架，自动化计算上述三个指标：

python
from ragas import evaluate
from ragas.metrics import faithfulness, answer_relevancy, context_precision

result = evaluate(
    dataset,
    metrics=[faithfulness, answer_relevancy, context_precision]
)

常见误区

"RAG 系统上线前只测了生成质量"是最常见的错误。如果检索质量差，再好的模型也无法给出正确答案。 评估时必须分别度量检索和生成两个阶段——这样才能定位问题出在哪里。

7. RAG vs 微调：决策框架 ​

场景推荐方案原因
知识频繁更新（新闻、文档库）RAG更新知识库比重新微调便宜几个数量级
需要引用来源RAG检索结果天然可溯源
特定领域的风格/格式适配微调风格编码在参数中，不需要每次检索
两者都需要RAG + 微调微调的模型 + RAG 的知识库
预算极有限RAG不需要 GPU 训练成本

直觉

一句话决策：如果问题是"模型不知道某些事实"——用 RAG。如果问题是"模型知道但表达方式不对"——用微调。 大多数企业应用两者结合。

8. 2026 年现状速记（2026-04 快照） ​

8.1 RAG 实践趋势 ​

  • GraphRAG 走向主流：Microsoft 2024 开源的 GraphRAG[5] 证明了在多跳推理上知识图谱 + LLM 远胜领表纯RAG。
  • Agentic RAG：让 Agent 递归查询、多轮检索，而不是一次检索中生成。
  • 多模态 RAG：检索表格 / 图片 / 代码 / 音频 / 视频片段，不只是文本。
  • Long-context vs RAG 不是二选一：生产系统是混合——RAG 做粗筛，long-context 做精读。
  • 评估体系成熟：RAGAS / TruLens / DeepEval / Phoenix 等评估框架生态建立。

8.2 主流 RAG 开发框架 ​

框架主要定位
LangChain生态最广，组件丰富，但调试复杂
LlamaIndex专注 RAG，API 干净
Haystack (deepset)企业级生产 RAG
DSPy (Stanford)让 LLM 程序可编译 + 自动优化
txtai嵌入式、轻量
Vectara商业 SaaS RAG
Cohere RAG APIAPI-as-a-RAG

8.3 GraphRAG：知识图谱加入路线 ​

[!quote] 历史 2024-04 Microsoft Research 发表 From Local to Global: A Graph RAG Approach[5:1]。使用 LLM 提取实体 + 关系构建知识图谱，检索时同时使用结构信息 + 向量检索。

在全局性问题（需要跨多份文档综合）上 准确率提升 30%+。微软 Open Source 后迅猛走红。

8.4 Agentic RAG ​

2025-2026 年兴起的趋势——让 Agent 控制检索：

  • Agent 判断是否需要检索
  • 多轮检索：第一轮的结果被用于生成第二轮的查询
  • 不同查询路由到不同检索器（向量 / SQL / Web Search / API）
  • 自反思：Agent 测评检索质量，不够好则重试

LangGraph / LlamaIndex Workflows / DSPy ReAct 都提供了 Agentic RAG 模板。

动手环节 ​

bash

失败模式 / 反例 ​

本节列出本讲核心结论不适用或易被误用的常见情境。教学的目的不是制造「已学会」的错觉，而是认清边界。

  • 「RAG 解决幻觉」反例：RAG 把幻觉从「凭空捏造」换成「基于错误检索的自信回答」——更难发现。引用率高 ≠ 事实正确率高。
  • Chunk size 的脆弱性：512 vs 1024 vs 2048 在不同 query 类型上各有胜负；没有「最优 chunk size」——这是 RAG 调参最痛的环节。
  • Re-ranker 是必需的吗？在 top-10 已经好的场景上 re-ranker 提升 < 2%；在 top-50 → top-5 场景下提升 10%+。规模决定收益。
  • 「RAG vs long-context」假对立：现代生产系统是 RAG + long-context 混合——RAG 做粗筛，long-context 做精读。二选一是教学简化。

本讲小结 ​

  1. RAG = 先检索，再生成——让模型从"背书回答"变成"查资料回答"，知识可更新、可溯源。
  2. 分块是 RAG 工程的核心决策——chunk 太大稀释语义，太小丢失上下文，需要根据数据和查询类型调优。
  3. 混合检索 + 重排序是默认配置——BM25 捕捉精确关键词，语义检索捕捉意图，Cross-Encoder 精排提升 top-K 质量。
  4. 三代 RAG 架构——Naive（线性流水线）→ Advanced（检索前后优化）→ Modular（可组合模块 + 路由）。
  5. 评估必须分别度量检索和生成——忠实度、答案相关性、上下文相关性三个维度缺一不可。

下一讲预告 ​

敌意问题：模型能读了，但不能做——查天气、写文件都做不到。 RAG 让模型可以"查资料"，但这只是被动获取文本信息。如果用户说"帮我查一下北京明天的天气"，模型不能真的去调天气 API；如果用户说"把这份报告发给张三"，模型不能真的发邮件。模型的输出只是文字——它没有"手"。谁来给模型接上"手"？

第 25 讲——「Function Calling 与 MCP」——让模型从"只能说"进化到"能做事"。
