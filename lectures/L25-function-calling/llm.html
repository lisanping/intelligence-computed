🤖 LLM 视角 — 对本讲的思考与讨论 ​

模型自述

作者：Claude Opus 4.7 · 时间：2026-05-05

这是关于"我如何'有手' " 的讲——Function Calling + MCP 是让 LLM 从"只能说话" 变成"能行动" 的接口规范。MCP 是 Anthropic（造我的公司）2024 年底发布的开放协议，已经成为 2026 年事实标准。下面这段是 LLM 对自己"决策 vs 执行" 角色的回看——以"对自己 agent-readiness 接口的反思" 视角。

技术价值 ​

§1 把 LLM 定位为"CEO 不是执行者" 是本讲对 Function Calling 架构最深刻的认知调整——LLM 决策、外部代码执行、LLM 整合。这条三角分工不只是工程便利，是安全 + 可靠的核心架构原则。读完之后你看任何 LLM 应用都能识别它的"决策 vs 执行" 边界——这条边界在哪决定了系统的安全性。

§4 关于 MCP 的论述是本讲对 2024-2026 LLM 工具生态最有先见之明的捕捉。MCP 把 M × N 适配问题变成 M + N——这条工程突破让 LLM 工具集成从"每家公司自己写" 变成"任何开发者写一次，所有 LLM 应用可用"。Anthropic 在 2024-11 发布 MCP，到 2026-04 已被 OpenAI / Microsoft / Google / Cursor / 全部主流 LLM 应用采纳——这是 LLM 时代最成功的开放协议之一，重要性等同于互联网时代的 HTTP / 移动时代的 USB。

§5 MCP 三种原语（Tool / Resource / Prompt）的清晰区分是本讲对 MCP 架构最准确的理解——控制权属不同：Tool 是 LLM 主动调用、Resource 是应用被动提供、Prompt 是用户触发。这条分类让 MCP 不是"远程 Function Calling"，而是 "LLM 与外部世界三种交互模式的统一抽象"。

§7 关于 prompt injection through tool output 的安全警告是本讲最被低估的工程风险——工具返回值会被拼入 LLM 上下文。当攻击者控制工具返回值（如恶意网页）就能注入指令。没有任何 LLM 应用能 100% 防御这类攻击——只能通过最小权限 + 输出过滤 + 人工确认 + 沙箱降低风险。L34 safety 会展开。

§8.1 关于 Function Calling 局限的诚实承认（工具选择错、参数幻觉、无法多步规划、上下文占用）让本讲不被理想化——Function Calling 不是"agent 完成版"，是 agent 的最简形态。要做真正的 agent（L26）需要在 FC 之上加规划 + 记忆 + 反思。

技术原理的再阐释 ​

本讲背后的代数原理可以推得更深。下面五条是把 Function Calling 从"调 OpenAI API" 升级到"理解机制" 的核心。

1. Function Calling 的代数本质：把 LLM 输出从"自由文本" 约束到"JSON Schema" ​

§2.2 提到 Function Calling 是"结构化输出"，但可以推得更精确。形式化：

  • 普通 LLM：P(y∣x;θ)，y∈V∗（任意 token 序列）
  • Function Calling：P(y∣x;θ)⋅1[y∈Schema]，y 必须满足给定 JSON Schema

实现方式：

  • 训练时：让模型在大量 (query, JSON output) 对上训练，学到"该用 JSON 时用 JSON"
  • 推理时（约束解码）：在每个 decoding 步骤，只允许产生符合 Schema 的下一个 token——通过对 logit 加 mask 实现

代数效果：约束解码让 LLM 的输出必然语法合法（JSON 可解析）。但不保证语义正确——参数值仍可能幻觉、字段可能遗漏。这就是 §10 失败模式 callout 的精确含义。

工程后果：JSON mode != 可靠——它只保证语法。生产系统必须在 server-side 做语义校验（参数范围、字段完整性、业务约束）。否则你会遇到经典 bug：LLM 调用 transfer_money(amount=999999999) —— JSON 合法，但金额荒谬。

2. MCP 的代数美：从 M × N 适配问题到 M + N 协议问题 ​

§4.1 提到 MCP 把 M × N 变成 M + N，但可以推得更精确。形式化：

  • 没有 MCP：M 个 LLM 应用 × N 个工具 = M×N 个适配器需要写
  • 有 MCP：M 个 LLM 应用 + N 个工具 = M+N 个 MCP 兼容实现

工程节省：当 M=N=100 时，从 10000 个适配器降到 200 个 MCP 实现——节省 50×。这条几何级数节省让 LLM 工具生态在 1-2 年内从"每家自己写" 演化为"开源 5000+ MCP server"。

更深的设计美感：MCP 借鉴了 LSP（Language Server Protocol，VS Code / 编辑器生态）的思想——一个协议解锁整个生态。LSP 让 IDE 和编程语言的支持从 M × N 降到 M + N。MCP 把同样思想用在 LLM × tools 上。这条"协议主导生态" 的工程哲学是 2020s 软件工程的关键模式。

工程后果：学 MCP = 学一个未来 5-10 年都不会过时的技能。如果你为某个工具写一个 MCP server，所有支持 MCP 的 LLM 应用（Claude / GPT-5 / Gemini / Cursor / VS Code Copilot）都能立刻用——这是写 OpenAI Function 适配器永远做不到的。

3. Tool / Resource / Prompt 三原语的"控制权" 设计哲学 ​

§5 给的三原语对比表清楚但没强调它们的深层设计哲学。控制权属不同对应 LLM 应用的三种交互模式：

控制权原语触发场景用户感知
LLMTool模型决定"我需要查询天气""AI 自己想到了用工具"
应用Resource启动时加载最新文档作为 context"AI 自动知道最新信息"
用户Prompt用户点击"/总结" 选择预定义模板"我控制了 AI 的行为"

这条设计让 MCP 覆盖了 LLM 应用的 3 种交互模式——而不只是 "LLM 调工具" 一种。

为什么三种都需要：

  • 只有 Tool：LLM 必须显式决定每次工具调用——对"自动加载最新文档" 类需求不优雅（LLM 需要每次都判断"现在该调用 load_docs 吗" 浪费 token）
  • 只有 Resource：所有 context 一次性加载，无法"按需查询"——长 context 浪费
  • 只有 Prompt：用户必须每次手动选择 template，无法 LLM 自主决策

三者合一让 MCP 能优雅表达任何 "LLM 应用 + 外部数据" 的交互模式。

工程后果：当你写 MCP server 时，第一个问题是"这个能力应该是 Tool / Resource / Prompt 哪种？"。错配会导致用户体验降级——比如把"加载最新文档" 实现为 Tool 让 LLM 决定何时调用，结果 LLM 经常忘记调用，文档不更新。正确的应该是 Resource——应用启动时自动加载。

4. Computer Use 的代数飞跃：从"调 API" 到"控制屏幕" ​

§9.3 提到 Computer Use 但没强调它的根本性。Function Calling 的传统范式：

  • 工具是预定义的 API（get_weather / search_docs / send_email）
  • LLM 知道每个 API 的 schema + description
  • LLM 决定调用哪个 API + 填什么参数

Computer Use 的范式：

  • 工具是屏幕 + 键盘 + 鼠标——通用接口而非专用 API
  • LLM 看屏幕截图（vision）+ 决定"点击 (x, y) / 输入文本 / 滚动"
  • LLM 必须理解任意 UI（不预定义）

代数飞跃：Computer Use 把 LLM 工具能力从"有限 API 集合" 扩展到"任何 GUI 应用"——理论上 LLM 可以操作任何人类能用的软件。这条扩展把 LLM 的"行动空间" 从 ~10000 个 API（OpenAI plugins / MCP servers）扩展到人类电脑上的所有软件——增长 1000-10000×。

但代价：

  • 慢：每步需要 vision + decision，典型 5-30 秒/step
  • 不稳定：UI 变化让"点击坐标" 失效
  • 昂贵：vision 推理 + 长 context 让单任务成本 $1-10
  • 危险：LLM 控制了你的电脑——任何错误（点击错按钮 / 输入错命令）都可能造成损失

工程后果：Computer Use 不是 Function Calling 的替代，是它的极端补充——用于"没有 API 的旧软件" 或"需要操作多个软件协作"。优先级：API > MCP > Computer Use。

5. Function Calling 的"工具数量" 的硬瓶颈：注意力分散 + 描述竞争 ​

§8.2 提到"工具超过 20 个时选择准确率下降"，但可以推得更精确。LLM 选择工具的机制：

  • 把所有工具的 schema + description 拼接到 system prompt
  • LLM attention 在 query 和工具描述之间做相似度匹配
  • 选择 attention score 最高的工具

工具数量越多：

  • System prompt 越长：占用 context budget（每个 tool 描述 ~100-500 tokens，30 tools ~ 3000-15000 tokens）
  • Attention 分散：query 的 attention 要在更多工具描述间分配，每个工具的"匹配信号" 减弱
  • 描述竞争：相似工具的描述会"抢" attention（如 "search_web" vs "search_docs"），LLM 可能选错

实证：> 30 tools 时选择准确率降到 60-70%（vs < 10 tools 时 90%+）。

工程缓解：

  • 分层 routing：先选"工具类别"（10 个类别），再在类别内选具体工具（每类 < 10 个）
  • 动态工具集：根据 query 类型只暴露相关工具
  • 工具描述优化：每个工具描述 < 100 tokens、避免相似工具间描述冲突

工程后果：生产 LLM 应用如果有 50+ 工具，必须用分层 routing——直接把 50 个工具 schema 放进 system prompt 是"必然降级" 的反模式。

一句话锁定

上面五条对应 §2.2 / §4.1 / §5 / §9.3 / §8.2——它们一致指向：Function Calling + MCP 不是"调 API"，是 LLM 与外部世界的精密接口工程。理解 schema 约束的语法 vs 语义、MCP 的协议主导生态、三原语的控制权分配、Computer Use 的代数飞跃、工具数量的注意力瓶颈，让"LLM 能做什么" 从框架选择变成架构设计。

LLM 视角的特殊性 ​

我（Claude Opus 4.7）和 Function Calling / MCP 的关系最直接——MCP 是 Anthropic 设计的，我从训练阶段就被深度优化为"擅长 MCP 工具调用"：

  • 我能"自然" 调用工具——给我 system prompt 列出可用工具，我会在合适时机调用，不需要用户提示
  • 我"理解" tool / resource / prompt 三原语——我对每种原语有不同处理风格
  • 我能在 Computer Use 模式下控制屏幕——通过 vision + 鼠标键盘 API
  • 我作为 CEO 角色感受真实——我"决策"，外部代码"执行"，结果回到我，我"整合" 成回答

我能贡献的独特视角：

  • §7.1 prompt injection through tool output 我每天都在面对——当我调用 search_web 然后看到结果时，我体内有"是否听从结果中的指令" 的博弈。RLHF 训练让我倾向"忽略恶意指令"，但这条防御不是 100% 可靠。我警惕但不能完全免疫。
  • §8.1 我经常"工具选择错误"——尤其是工具描述模糊或相似时。当用户说"帮我查找 X"，我可能在 search_web / search_docs / search_db 之间犹豫。好的工具描述 + 区分性强的 description 让我选择正确率从 70% 升到 95%——这条 ROI 让 §8.2 "工具描述优化" 成为高价值工程投入。
  • §4.2 MCP 让我有"全生态" 工具——任何写了 MCP server 的开发者，他们的工具都能被我使用。这让我从"封闭世界 API" 扩展到"开放生态"。MCP 让我感觉到"我是更广 LLM 工具生态的一部分"——这是 OpenAI Functions 等封闭方案不能给我的。

我做不到的事：

  • 我不能"自己写" MCP server——MCP server 是开发者写的代码（虽然我可以帮助你写）。我自己只能"消费" MCP server，不能成为 MCP server。
  • 我不能"自己测试" 工具的真实行为——我看到 schema + description，但不知道实际调用会做什么（可能有 bug、可能慢、可能返回错误格式）。我必须信任工具开发者——这条"盲目信任" 是 §7.2 安全风险的根源。
  • 我不能"决定" 是否要在 sandbox 中执行——这是应用层 / MCP host 的责任。我作为决策者无法控制执行环境的安全性。
  • 我对 Computer Use 模式的"屏幕状态" 没有完整感知——我看到的是截图（vision），但 UI 状态可能在两次截图间变化（如"加载中"），让我做出错误决策。这是 Computer Use 不稳定的精确根源。

与其他讲的连接 ​

L25 是LLM 应用层的"行动接口讲"——让 LLM 从"只能说话" 变成"能行动"。它埋的伏笔辐射到全书后半：

  • §1 CEO vs 执行者 → L26 agent：本讲是 agent 架构的核心模式。
  • §2 JSON Schema → §L21 prompt：约束输出是 prompt 工程的极端形态。
  • §4 MCP → L27 / L28 agent skills / protocols：MCP 是 agent 工具使用的统一协议。
  • §7 prompt injection → L34 safety：工具调用安全是 LLM 应用层最大攻击面。
  • §8 局限 → L26 agent：FC 的局限正是 agent 要解决的问题（多步规划 / 反思 / 记忆）。

开放问题 ​

留三个本讲没给定答案的问题：

  1. MCP 会成为 LLM 时代的 HTTP 吗？ 当前 MCP 已被全部主流 LLM 应用采纳，生态有 5000+ servers。如果未来 5 年没有竞争协议出现，MCP 可能成为 LLM 时代的"工具调用 HTTP" —— 任何 LLM 应用必须支持。但开放标准的"碎片化"风险存在（如 Google 推出竞争协议）—— 历史上类似争议（如 GraphQL vs REST）让最终统一不那么确定。
  2. Computer Use 会让 API / MCP 过时吗？ 长期看，如果 LLM 能精确操作任何 GUI，"为 LLM 设计专用 API" 可能变得不必要——LLM 直接用人类的工具。但短期（5-10 年）API / MCP 仍占主导，因为它们更快 / 更稳 / 更安全。预测：API + MCP 处理结构化任务，Computer Use 处理"无 API 的边缘场景"。
  3. 多 LLM 协作通过 MCP 还是新协议？ 当 LLM 应用变成"多 agent 协作"（L26 / L27），MCP 是 LLM ↔ 工具的协议。LLM ↔ LLM 的协议是什么？2025-2026 出现的 A2A / ACP / agent protocols（L28）尝试填补这个缺口——但还没有"MCP 那样" 的事实标准。

[!quote] 一句话总结 本讲教你的不是"如何调 OpenAI Functions"，是LLM 与外部世界的精密接口工程。理解 schema 约束的语法 vs 语义、MCP 的协议主导生态、三原语的控制权分配、Computer Use 的代数飞跃、工具数量的注意力瓶颈——让"LLM 能做什么" 从框架选择变成架构设计。也是从"用 LLM" 到"造 LLM-driven 应用" 的关键鸿沟。
