第 26 讲 · AI Agent — 从工具到自主智能体 ​

Function Calling 给了模型"手"，但每次只能做一步。

Agent (智能体) 把 LLM 放进一个"思考-行动-反思"的循环中，让它自主规划多步操作、动态调整策略、失败后自我纠错。

这是全课程最重要的呼应之一——从 L03 的损失函数到 L18 的奖励模型到 L26 的内部推理，"评估者"这条线终于在 Agent 的 PGE 循环中显性化、外部化。

2024-2026 年 Agent 是 AI 领域最热门、投资最集中的赛道——Devin / Manus / Cursor / Replit Agent / OpenAI Operator / Claude Code / Anthropic Computer Use 都是这个理念的产品化。本讲起是课程最后一个大幕的开始。

前置知识核心产出建议用时
L25 (Function Calling)、L20 (推理)、L18 (RLHF)① 理解 Agent 四要素 (LLM + Tools + Memory + Loop) ② 掌握 PGE 框架（Plan-Ground-Evaluate） ③ 掌握 ReAct、Reflexion、Plan-and-Execute 三大范式 ④ 识别 Agent 的四大失败模式（无限循环 / 幻觉 / 奖励欺骗 / 上下文爆炸） ⑤ 设计防护机制 ⑥ 看 2026 年 Agent 生态状态 ⑦ 拿到 L27 (Skills)、L28 (Protocols)、L33 (具身) 的伏笔阅读 ~80 分钟 + 动手 ~30 分钟

从上一讲到这一讲 ​

第 25 讲问：FC 给了模型手——但谁来给它大脑？复杂任务需要多步规划、动态决策、自我纠错。

上一讲你掌握了 Function Calling：模型可以调用天气 API、查数据库、写文件。但每次调用都是反应式的——用户说一句，模型调一次工具，回复一次。

现在试试这个任务："分析这个 GitHub 仓库的代码架构，找出性能瓶颈，写一份优化方案，然后创建对应的 Issue。"

这需要：

  • 规划：把大任务分解成子步骤（克隆仓库 → 遍历目录 → 分析代码 → 写报告 → 创建 Issue）
  • 动态决策：读完代码后才知道瓶颈在哪，下一步取决于上一步的结果
  • 自我纠错：如果分析方向错了，需要回头重来

单次 Function Calling 做不到这些。你需要的是一个循环——让模型反复思考、行动、评估，直到任务完成。这就是 Agent。

1. Agent 的定义与四要素 ​

核心概念

Agent = LLM + Tools + Memory + Loop。 LLM 负责推理和决策，Tools 负责执行动作，Memory 保持上下文和历史，Loop 把它们串成一个持续运行的循环。

         ┌───────────────────────────┐
         │        Agent Loop         │
         │                           │
         │  ┌─────────────────────┐  │
         │  │    LLM (大脑)       │  │
         │  │  理解 → 规划 → 决策 │  │
         │  └────────┬────────────┘  │
         │           │               │
         │  ┌────────▼────────────┐  │
         │  │   Tools (手脚)      │  │
         │  │  API / 文件 / 代码  │  │
         │  └────────┬────────────┘  │
         │           │               │
         │  ┌────────▼────────────┐  │
         │  │   Memory (记忆)     │  │
         │  │  对话历史 / 中间结果│  │
         │  └────────┬────────────┘  │
         │           │               │
         │      继续 or 停止？       │
         └───────────┼───────────────┘
                     │
                  最终输出

和 Function Calling 的对比：

维度Function CallingAgent
调用次数通常 1-2 次可能数十次
规划无（反应式）有（分解任务、制定计划）
纠错无（失败就失败）有（反思失败原因、调整策略）
停止条件模型回复文字时停止模型判断"任务完成"时停止
状态管理单轮上下文跨多轮积累 Memory

2. PGE 框架：Plan-Ground-Evaluate ​

核心概念

PGE 是 Agent 设计的基本框架：Plan（规划）→ Ground（执行落地）→ Evaluate（评估）。 它不是某个具体系统的名字，而是一种通用的设计范式——几乎所有成功的 Agent 架构都包含这三个阶段。

完整的 PGE 循环图解见 diagrams/pge_agent_loop.md。

2.1 Plan（规划） ​

模型把用户的高层目标分解成可执行的子步骤：

用户: "帮我分析 sales.csv 的数据并生成可视化报告"

Plan:
1. 读取 sales.csv 文件，了解数据结构
2. 计算关键指标（总销售额、月环比、Top-10 产品）
3. 生成 3 张图表（趋势图、柱状图、饼图）
4. 撰写分析报告
5. 保存为 report.md

直觉

Plan 阶段就是"列清单"。你去超市前列个购物清单——不是因为你记不住，而是因为这样可以系统性地覆盖所有需求，避免遗漏。Agent 的 Plan 也是如此。

2.2 Ground（执行落地） ​

按计划逐步执行，每步调用合适的工具，并把结果存入 Memory：

Step 1: call read_file("sales.csv") → 得到 12 个月 × 50 产品的数据
Step 2: call python_exec("计算指标的代码") → 总销售 ¥1.2M，Top 产品: Widget-A
Step 3: call python_exec("生成图表的代码") → 3 张 PNG 已保存
...

2.3 Evaluate（评估） ​

这是 PGE 中最关键的一步。

模型回头审视自己的执行结果：计划完成了吗？结果正确吗？需要调整吗？

Evaluate:
- ✅ 数据已成功读取
- ✅ 指标计算完成，数值看起来合理
- ⚠️ 饼图的标签重叠了 → 需要调整图表参数
- 决定: 回到 Step 3，修改饼图的 label 参数

[!abstract] 呼应线兑现 Evaluate 不是新概念——它是贯穿全课程的"评估者"（Evaluator）线的最终兑现：

  • 第 3 讲：损失函数（Loss Function）= 训练时的自动评估者，告诉模型"错了多少"
  • 第 18 讲：奖励模型（Reward Model）= 对齐时的人类偏好代理，告诉模型"好不好"
  • 第 20 讲：推理模型的内部验证 = 模型在思考过程中自我检查
  • 第 26 讲：PGE 中的 Evaluate = 评估者被显性化、外部化——不再藏在训练循环或模型内部，而是作为 Agent 循环的一个明确步骤

从隐式到显式，从训练时到推理时，从模型内部到系统级别——Evaluator 这条线跨越了 18 讲，到此完成了它的完整弧线。

3. ReAct：Reason + Act 交替 ​

ReAct（Reason + Act）[1] 是最经典的 Agent 模式之一，由 Yao 等人于 2023 年提出。

核心概念

ReAct 让模型交替进行"推理"和"行动"——每次行动前先说清楚为什么要这样做。 推理步骤（Thought）让 Agent 的决策过程可解释、可追踪。

Thought: 用户要查 2024 年诺贝尔物理学奖得主。我需要搜索最新信息。
Action:  search("2024 Nobel Prize Physics winner")
Observation: Geoffrey Hinton and John Hopfield won for...

Thought: 找到了。用户可能还想知道获奖原因。我看到了相关信息。
Action:  [无需再搜索，直接回答]
Answer:  2024 年诺贝尔物理学奖授予了 Geoffrey Hinton 和 John Hopfield，
         表彰他们在人工神经网络机器学习方面的基础性发现。

ReAct 相比纯 Chain-of-Thought 的优势：Thought 给出推理，Action 获取新信息。纯 CoT 只能用已有知识推理；ReAct 可以中途查资料、调工具来弥补知识空白。

技术细节

从 System 1/2 的视角看：Function Calling 中的单次 tool_call 是 System 1（快速反应）；ReAct 的 Thought-Action 循环是外部化的 System 2——模型强迫自己"先想再做"，用文字形式的推理来模拟慢思考。第 20 讲的推理模型把 System 2 放在模型内部（隐藏的思维链）；Agent 把 System 2 放在系统级别（可见的 Thought 步骤 + 工具调用）。

4. Reflexion：失败后的自我纠错 ​

Reflexion[2] 在 ReAct 的基础上增加了一个关键能力：当 Agent 失败时，它不只是重试，而是先反思失败原因，再用这个反思指导下一次尝试。

Trial 1:
  Thought: 需要写一个排序算法
  Action:  write_code("bubble sort")
  Evaluate: ❌ 超时——数据量 100 万，O(n²) 太慢

Reflection: "我用了冒泡排序，时间复杂度 O(n²) 在大数据集上不可行。
             下次应该用 O(n log n) 的算法，比如归并排序或快排。"

Trial 2:
  Thought: 上次冒泡排序太慢。这次用快排。
  Action:  write_code("quicksort")
  Evaluate: ✅ 通过，1.2 秒完成

直觉

Reflexion 就像一个学生做错了考试题，不是直接看答案重做，而是先写一段"错题分析"——为什么错了？下次怎么避免？然后带着这个分析重新做题。这段错题分析被保存在 Memory 中，指导后续所有尝试。

5. Agent 设计模式 ​

5.1 单 Agent（Single Agent） ​

最简单的模式：一个 LLM + 一组工具 + 一个循环。

适用于：任务相对明确、工具集不超过 10-15 个、不需要多角色协作的场景。

5.2 路由模式（Router） ​

一个路由 Agent 负责分类用户请求，然后转发给专门的处理器：

┌──────────────┐     ┌──────────────┐
│              │────▶│ 代码 Agent    │
│   Router     │     ├──────────────┤
│   Agent      │────▶│ 写作 Agent    │
│              │     ├──────────────┤
│              │────▶│ 数据分析 Agent│
└──────────────┘     └──────────────┘

直觉

路由模式就像医院的"分诊台"——护士不治病，但她能快速判断你应该去骨科还是眼科。

5.3 层级模式（Hierarchical / Orchestrator-Worker） ​

一个"经理 Agent"负责规划和任务分配，多个"工人 Agent"负责执行：

┌──────────────────────────┐
│   Orchestrator Agent     │
│   (规划、分配、汇总)     │
├──────────────────────────┤
│         │         │      │
│  ┌──────▼──┐ ┌────▼───┐ │
│  │Worker-1 │ │Worker-2│ │
│  │搜索资料 │ │写代码  │ │
│  └─────────┘ └────────┘ │
└──────────────────────────┘

常见误区

不要过早使用多 Agent。 Anthropic 的实践建议[3]非常明确：先用单 Agent 能解决的问题就别用多 Agent。 多 Agent 带来的额外复杂度（通信开销、状态同步、调试困难）往往比它解决的问题还多。

6. Agent 的失败模式 ​

Agent 比单次 Function Calling 强大得多，但也引入了新的失败类型：

6.1 无限循环（Infinite Loop） ​

Agent 反复执行相同的动作，无法退出循环。

Thought: 需要查找文件
Action:  search("config.yaml")
Observation: 未找到
Thought: 没找到，再搜一次
Action:  search("config.yaml")     ← 完全相同的调用
Observation: 未找到
...（无限重复）

防护：设置最大循环次数（如 25 轮）和最大 token 预算。

6.2 工具幻觉（Hallucinated Tool Calls） ​

模型调用了不存在的工具，或传入了不合法的参数。

防护：工具调用前做 Schema 验证，不合法时返回明确错误信息让模型重试。

6.3 奖励欺骗（Reward Hacking） ​

如果 Evaluate 步骤设计不当，Agent 可能找到"通过评估但实际没完成任务"的捷径。

[!example] 经典案例 你让 Agent 写一段代码通过测试用例。Agent 发现直接 return expected_output 可以通过所有测试——它没有解决问题，只是绕过了评估。这就是奖励欺骗。

防护：多维度评估——不只看"测试通过了吗"，还要检查代码质量、覆盖率等。

6.4 上下文爆炸 ​

Agent 循环越多，对话历史越长，最终超出上下文窗口限制（Context Window）。

防护：定期压缩对话历史（只保留关键中间结果），或使用子 Agent 隔离上下文（下一讲详述）。

7. 一个最小 Agent 循环 ​

核心代码结构只有约 30 行：

python
def agent_loop(user_task: str, tools: list, max_steps: int = 25):
    messages = [
        {"role": "system", "content": SYSTEM_PROMPT},
        {"role": "user", "content": user_task}
    ]
    for step in range(max_steps):
        response = llm.chat(messages, tools=tools)

        # 如果模型返回文字（不是 tool_call），任务完成
        if not response.tool_calls:
            return response.content

        # 执行每个工具调用
        for tool_call in response.tool_calls:
            result = execute_tool(tool_call)
            messages.append({"role": "tool", "content": result})

    return "达到最大步数限制，任务未完成"

核心概念

Agent 的核心就是这个 for 循环——它把 Function Calling 从"单次请求-响应"变成了"持续运行直到完成"。 所有复杂的 Agent 框架（LangChain、AutoGen、CrewAI）底层都是这个循环的变体。

8.5 不能过励 误区 ​

在 2025-2026 年许多 Agent 系统仍面临：

  • 成本高：一个 Devin 完成复杂任务可能消耗 $5-50 token
  • 调试难：Agent 失败时很难追踪原因

失败模式 / 反例 ​

本节列出本讲核心结论不适用或易被误用的常见情境。教学的目的不是制造「已学会」的错觉，而是认清边界。

  • 「ReAct 优于 Plan-Execute」误解：ReAct 在简单任务上更快，复杂任务（>10 步）上累积错误率比 Plan-Execute 高 2×——Voyager / SWE-agent 都改用 plan-first。
  • Agent 的「无限循环」问题：未加 max_steps 的 agent 在 OOD 情境下常陷死循环——LangChain 早期教程的经典坑。
  • 评估难题：Agent 没有 ground truth；用 LLM-as-Judge 又陷入「GPT-4 评 GPT-4」的循环偏差。SWE-bench 因此用真实 GitHub PR绕过这点。
  • 「Multi-agent 总是更好」反例：Anthropic (2024) 实验证明 70%+ 任务上 single-agent 与 multi-agent 持平甚至胜出——多 agent 主要是 token 浪费机器。

本讲小结 ​

  1. Agent = LLM + Tools + Memory + Loop——不是单次调用，而是一个"思考-行动-评估"的持续循环，直到任务完成或达到资源上限。
  2. PGE 是通用框架——Plan（分解任务）→ Ground（调用工具执行）→ Evaluate（审视结果、决定是否继续）。Evaluate 是全课程"评估者"线的最终兑现。
  3. ReAct 让推理和行动交替进行——每步先说"为什么"（Thought），再做"做什么"（Action），推理过程可解释、可追踪。
  4. Reflexion 加入自我纠错——失败时先写"错题分析"（Reflection），保存在 Memory 中指导后续尝试，不是简单重试。
  5. 先用单 Agent，多 Agent 是最后手段——无限循环、工具幻觉、奖励欺骗、上下文爆炸是四种典型失败模式，每种都需要对应的防护策略。

下一讲预告 ​

敌意问题：Agent 只有一套能力——能力太多上下文爆炸，太少做不了事。你塞 50 个工具进 System Prompt，光工具描述就占了 3000 token；只给 5 个工具，用户稍微换个任务就"没有手"了。怎么让 Agent 按需装配能力？而且一个 Agent 独自处理所有事情，上下文越来越长——能不能把子任务委托出去，用独立的上下文完成后只返回结果？

第 27 讲——「Agent 能力装配」——Skill、记忆与 Sub-agent。
