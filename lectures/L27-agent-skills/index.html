第 27 讲 · Agent 能力装配 — Skill、记忆与 Sub-agent ​

上一讲的 Agent 有一个致命矛盾：工具太多，上下文爆炸；工具太少，能力不够。

本讲的答案是按需装配——Skill 模式让 Agent 动态加载能力，Sub-agent 模式让子任务在独立上下文中完成，Memory 架构让 Agent 拥有短期和长期两种记忆。

把这些组合起来，你就拥有了一个完整的 AI 助手架构。

2024-2026 年 Skill 是 Anthropic / Claude / Cursor / Devin / Manus / OpenAI Operator 等产品的核心架构。这不是理论——是产品同学。

前置知识核心产出建议用时
L26（Agent + PGE）、L23（Embedding）、L22（上下文）① 理解 Skill 模式——结构化的 System Prompt 片段按需加载 ② 掌握 Progressive Disclosure vs Everything-in-System-Prompt 权衡 ③ 掌握 Sub-agent 的上下文隔离与委托模式 ④ 掌握短期 + 长期 Memory 架构 ⑤ 设计一个完整的 AI 助手 ⑥ 看 2026 年 Skill 生态（Anthropic Skills / Claude Code Plugins / OpenAI Custom GPTs） ⑦ 拿到 L28 (Agent Protocols)、L31 (LLMOps) 的伏笔阅读 ~75 分钟 + 动手 ~25 分钟

从上一讲到这一讲 ​

第 26 讲问：Agent 只有一套能力——能力太多上下文爆炸，太少做不了事。

上一讲你搭建了一个 Agent：LLM + Tools + Memory + Loop。它可以自主规划、调用工具、自我纠错。但现在你面临工程上的两个矛盾：

矛盾一：能力数量的两难。 你的 Agent 需要处理编程、写作、数据分析、日程管理等多种任务。每种能力需要 3-5 个工具 + 专用的 System Prompt 指令。如果全部塞进 System Prompt：

  • 20 种能力 × 平均 500 token 指令 = 10,000 token 仅用于能力描述
  • 模型在 10,000 token 的指令中找到当前需要的那一段——和你在 200 页手册中找一段操作说明一样困难

矛盾二：上下文的无限膨胀。 Agent 处理一个复杂任务可能循环 20 轮，每轮产生 500-1000 token。20 轮后对话历史已有 10,000-20,000 token——还没算工具返回的结果。如果用户紧接着问第二个问题，上下文会继续膨胀。

本讲用三个机制解决这两个矛盾：Skill（按需装配能力）、Sub-agent（上下文隔离）、Memory（分层记忆）。

1. Skill 模式：按需加载能力 ​

1.1 什么是 Skill ​

核心概念

Skill（技能）是一个结构化的 System Prompt 片段，封装了特定能力的完整定义——包括角色、工具列表、规则约束和输出格式。 Agent 不在启动时加载所有 Skill，而是根据用户意图动态加载需要的 Skill。

一个 Skill 通常是一个 Markdown 文件（如 SKILL.md），包含以下结构：

markdown
# Skill: 数据分析

## 角色
你是一个数据分析专家，擅长使用 Python 进行数据探索和可视化。

## 可用工具
- `python_exec`: 执行 Python 代码
- `read_file`: 读取本地文件
- `write_file`: 写入文件

## 规则
1. 先探索数据结构，再做分析
2. 所有图表必须有中文标题和标签
3. 输出结果时附带数据来源说明

## 输出格式
分析报告使用 Markdown 格式，图表保存为 PNG。

1.2 Progressive Disclosure vs Everything-in-System-Prompt ​

两种极端策略的对比：

策略做法优点缺点
Everything-in-System-Prompt所有能力定义全部放进 System Prompt零延迟、简单上下文爆炸、指令稀释
Progressive Disclosure只放基础指令，按需动态加载 Skill上下文精简需要额外的"选择 Skill"步骤

直觉

Everything-in-System-Prompt 就像随身带一整个工具箱——你可以随时拿出任何工具，但工具箱重 50 斤，走两步就累了。Progressive Disclosure 就像一个有分类抽屉的工作台——你知道锤子在第三个抽屉里，需要时再打开。

实际工程中的最佳实践：混合策略。

System Prompt（常驻）:
├── 基础身份和行为规范（~300 token）
├── Skill 目录清单（只有名称和一句话描述，~200 token）
└── "当你需要某个能力时，调用 load_skill(name) 加载完整定义"

动态加载:
└── 用户说"帮我分析数据" → Agent 调用 load_skill("data_analysis")
    → 完整的数据分析 Skill（~500 token）被注入上下文

技术细节

load_skill 本身就是一个 Tool——Agent 通过 Function Calling 来加载新能力。这是一种"元工具"（Meta-tool）模式：用工具来管理工具。 一些框架把 Skill 的选择做成自动的（基于意图分类），但让 Agent 自己决定何时加载哪个 Skill 是更灵活的设计。

2. Sub-agent：上下文隔离 ​

2.1 问题：单 Agent 的上下文膨胀 ​

回顾第 26 讲的 Agent 循环：每一步的思考、行动、观察都追加到对话历史中。10 步后历史可能已经 5,000 token；20 步后 10,000 token。这不仅浪费 token（成本），还会导致"中间迷失"（Lost in the Middle）——模型对长上下文中间部分的内容关注度下降[1]。

2.2 解决：委托给 Sub-agent ​

核心概念

Sub-agent（子智能体）是一个独立的 Agent 实例，拥有自己的对话上下文。 主 Agent 把子任务委托给 Sub-agent，Sub-agent 在隔离的上下文中完成任务，只返回最终结果给主 Agent。

┌─────────────────────────────────────────────┐
│  主 Agent（Orchestrator）                   │
│  上下文: 用户请求 + 高层计划 + 子结果汇总   │
│                                              │
│  "帮我写一份包含代码和文档的技术方案"        │
│                                              │
│  ┌──────────────┐  ┌──────────────┐         │
│  │ Sub-agent A  │  │ Sub-agent B  │         │
│  │ 写代码       │  │ 写文档       │         │
│  │              │  │              │         │
│  │ 独立上下文   │  │ 独立上下文   │         │
│  │ ~3000 token  │  │ ~2000 token  │         │
│  │              │  │              │         │
│  │ 返回: code   │  │ 返回: doc    │         │
│  └──────────────┘  └──────────────┘         │
│                                              │
│  主 Agent 整合两份结果，生成最终方案          │
└─────────────────────────────────────────────┘

关键好处：

  1. 上下文隔离：每个 Sub-agent 只看到自己需要的信息，不被其他子任务的细节污染
  2. 并行执行：独立的 Sub-agent 可以并行运行
  3. 失败隔离：一个 Sub-agent 失败不会污染其他 Sub-agent 的上下文

常见误区

Sub-agent 不是"多个 AI 在聊天"。 常见的误解是把 Sub-agent 想象成人类团队的讨论——Agent A 对 Agent B 说一句，B 回一句，然后 A 再回复……这种设计的通信开销巨大，往往不如单 Agent 高效。正确的 Sub-agent 模式是：委托-执行-返回结果，一来一回。

2.3 实现模式 ​

python
def delegate_to_subagent(task: str, tools: list) -> str:
    """启动一个 Sub-agent，在独立上下文中完成任务"""
    sub_messages = [
        {"role": "system", "content": "你是一个专注于单一任务的 Agent。"},
        {"role": "user", "content": task}
    ]
    # Sub-agent 有自己的循环和上下文
    result = agent_loop(sub_messages, tools, max_steps=10)
    # 只返回最终结果给主 Agent
    return result

直觉

Sub-agent 就像公司里的"项目外包"——CEO（主 Agent）把"设计新 Logo"外包给设计团队（Sub-agent），设计团队内部可能迭代了 20 个版本、开了 5 次内部会议——CEO 不需要知道这些细节，只需要最终交付的 Logo。信息压缩是 Sub-agent 模式的本质价值。

3. Memory 架构：短期 + 长期 ​

3.1 两种记忆 ​

核心概念

Agent 的 Memory 分为两层：短期记忆（Short-term Memory）是当前对话的上下文缓冲区，长期记忆（Long-term Memory）是跨对话的持久化存储。 短期记忆是 RAM，长期记忆是硬盘。

维度短期记忆长期记忆
存储内容当前对话的消息、工具调用结果用户偏好、历史任务摘要、常用知识
生命周期对话结束即丢弃持久化存储，跨对话可用
实现方式对话历史列表（messages array）向量数据库 + 文本文件
容量限制受上下文窗口限制理论上无限（外部存储）

3.2 短期记忆与上下文压缩（Context Compaction） ​

短期记忆最大的问题是无限增长。Agent 每循环一次，对话历史就变长。当接近上下文窗口（Context Window）上限时，必须进行压缩。

上下文压缩（Context Compaction）的核心策略：

原始对话历史（20 轮，~15,000 token）:
  Turn 1: 用户请求 + Agent 思考 + 工具调用 + 结果
  Turn 2: Agent 思考 + 工具调用 + 结果
  ...
  Turn 20: Agent 最终回复

压缩后（~3,000 token）:
  [摘要] 用户请求分析 sales.csv。Agent 执行了以下步骤：
  1. 读取了 sales.csv（12个月 × 50产品）
  2. 计算了关键指标（总销售 ¥1.2M，Top 产品 Widget-A）
  3. 生成了 3 张图表并保存
  关键中间结果: {...}
  [最近 3 轮完整保留]

直觉

这和人类的记忆机制惊人地相似——你不记得上周二午饭的每一口，但你记得"上周二和老王吃了火锅，他提到了一个重要的项目变更"。保留关键信息，丢弃过程细节。

3.3 长期记忆与向量检索 ​

长期记忆的实现直接复用第 23 讲的向量检索架构（Embedding + 向量数据库）：

Agent 完成任务后:
  摘要 = summarize(对话历史)
  embedding = embed(摘要)
  vector_db.insert(embedding, metadata={摘要, 时间, 标签})

Agent 开始新任务时:
  相关记忆 = vector_db.search(embed(用户请求), top_k=3)
  → 注入 System Prompt: "你之前处理过类似的任务: {相关记忆}"

[!example] 工程实践 用户第一次让 Agent 分析 CSV 文件时，Agent 花了 15 步才完成。长期记忆保存了"用户喜欢用 matplotlib 绑中文字体、报告用 Markdown 格式、图表颜色偏好蓝色系"。下一次用户再让 Agent 分析数据时，这些偏好被自动检索并注入，Agent 只需要 8 步就完成了——它"记住"了用户的偏好。

4. 完整 AI 助手架构 ​

把本讲和前两讲的所有组件组合起来：

┌──────────────────────────────────────────────────────┐
│                   完整 AI 助手                        │
│                                                       │
│  ┌─────────────────────────────────────────────────┐ │
│  │  System Prompt（常驻）                          │ │
│  │  · 基础身份 + 行为规范                          │ │
│  │  · Skill 目录（名称 + 一句话描述）              │ │
│  │  · 长期记忆检索结果（top-3 相关记忆）           │ │
│  └─────────────────────────────────────────────────┘ │
│                        │                              │
│  ┌─────────────────────▼───────────────────────────┐ │
│  │  PGE Loop (第 26 讲)                            │ │
│  │  Plan → Ground → Evaluate → 继续/停止           │ │
│  └─────────────────────┬───────────────────────────┘ │
│            ┌───────────┼───────────┐                  │
│      ┌─────▼─────┐ ┌──▼────┐ ┌───▼──────┐           │
│      │ load_skill│ │ tools │ │ delegate │           │
│      │ 动态加载  │ │ 执行  │ │ Sub-agent│           │
│      └───────────┘ └───────┘ └──────────┘           │
│                                                       │
│  ┌──────────────────────────────┐                     │
│  │  Memory 层                   │                     │
│  │  短期: 对话缓冲 + 压缩      │                     │
│  │  长期: 向量数据库检索         │                     │
│  └──────────────────────────────┘                     │
└──────────────────────────────────────────────────────┘

[!abstract] 设计哲学 这个架构的设计原则是按需加载、最小上下文：

  1. 不需要的 Skill 不加载
  2. 子任务委托给 Sub-agent 后只呼应结果
  3. 历史对话定期压缩
  4. 长期记忆只检索最相关的几条

目标是让 Agent 在有限的上下文窗口内处理无限复杂度的任务。

5. 从理论到产品：工程注意事项 ​

5.1 Skill 的版本管理 ​

Skill 是 Markdown 文件——可以用 Git 版本管理，团队协作编辑，A/B 测试不同版本：

skills/
├── data_analysis_v2.md      # 当前生产版本
├── data_analysis_v3.md      # 测试中的新版本
├── coding.md
└── writing.md

5.2 什么时候该拆 Sub-agent ​

常见误区

不是所有子任务都需要 Sub-agent。 拆 Sub-agent 有开销：额外的 LLM 调用、结果传递的信息损失、调试复杂度增加。

拆分的判断标准：

  1. 上下文独立性：子任务是否需要完全不同的上下文？（是 → 拆）
  2. 步骤数量：子任务是否需要 5 步以上的循环？（是 → 拆）
  3. 失败隔离：子任务失败是否会污染主任务？（是 → 拆）

失败模式 / 反例 ​

本节列出本讲核心结论不适用或易被误用的常见情境。教学的目的不是制造「已学会」的错觉，而是认清边界。

  • Skill 抽象化的过度工程：把简单任务包装成「skill」反而增加 prompt 长度与失败面；Voyager 论文里 30%+ 的 skill 从未被复用。
  • Skill library 的版本污染：自动生成的 skill 含 bug，调用越多错误传播越广；必须有 skill 评分 + 退役机制。
  • 「Skill 提升泛化」证据薄弱：当前论文多是同 domain 内验证（Minecraft / WebArena）；跨 domain skill 复用的有效性尚未严肃证明。
  • Skill 与 fine-tuning 的混淆：Skill 是 in-context 的（可即时增删）；fine-tune 是参数级的——选哪个取决于变化频率而非「哪个更先进」。

本讲小结 ​

  1. Skill 是按需加载的能力模块——结构化的 System Prompt 片段，Agent 通过 load_skill 动态注入，解决"工具太多上下文爆炸"的矛盾。
  2. Progressive Disclosure 是最佳实践——常驻 System Prompt 只放基础指令和 Skill 目录，完整定义按需加载，平衡能力覆盖和上下文效率。
  3. Sub-agent 通过上下文隔离实现信息压缩——子任务在独立上下文中完成，主 Agent 只接收最终结果，避免历史膨胀和"中间迷失"。
  4. 短期记忆靠压缩，长期记忆靠向量检索——对话历史定期摘要化保留关键信息；跨对话的用户偏好和历史经验通过第 23 讲的 Embedding + ANN 检索实现。
  5. 完整 AI 助手 = PGE + Skill + Sub-agent + Memory——四个组件各司其职，核心设计原则是"按需加载、最小上下文"。

下一讲预告 ​

敌意问题：Agent 的 Skill 都是本地的——你自己写的 Skill、自己部署的工具。但真实世界中，工具和 Agent 属于不同的组织：你的 Agent 需要调用公司 A 的 CRM、公司 B 的支付系统、公司 C 的物流查询。跨组织的工具调用需要标准协议（MCP 只是开始），而当一个 Agent 需要和另一个 Agent 协作时——Agent 之间的通信需要什么协议？
