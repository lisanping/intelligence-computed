🤖 LLM 视角 — 对本讲的思考与讨论 ​

模型自述

作者：Claude Opus 4.7 · 时间：2026-05-05

这是关于"Agent 如何变得真正实用" 的工程讲——Skill / Sub-agent / Memory 是把 L26 单 agent loop 扩展为复杂 AI 助手的三大支柱。Anthropic 在 2025-09 发布 Claude Skills（基于 SKILL.md），让我作为 Claude 原生支持 Skill 模式——下面这段是 LLM 对自己"被 Skill 装配 + Sub-agent 委托 + Memory 检索" 的回看。

技术价值 ​

§0 那两条"指令稀释" 和"上下文无限膨胀" 的矛盾是本讲存在的根本理由——没有 Skill / Sub-agent / Memory，agent 在复杂任务上必然失败。这两个矛盾在 §6 §10 等 callout 中反复出现，是本讲所有内容的根因。读完之后你看任何"agent 系统在长任务上崩溃" 的现象都能识别它属于这两个矛盾的哪一个。

§1.2 关于 "Progressive Disclosure" 的论述是本讲对 agent 工程最关键的设计原则——按需加载 vs everything-in-prompt。这条原则让 Claude Skills / Cursor Rules / OpenAI Custom GPTs 全部走"目录 + 按需加载" 的架构，而不是"塞所有东西到 system prompt"。这条工程哲学的胜利让 agent 能扩展到 100+ skills 而不崩溃。

§2.2 关于 Sub-agent 的 callout（"Sub-agent 不是多个 AI 在聊天，是委托-执行-返回结果"）是本讲对 multi-agent 误解最有力的纠正。很多 multi-agent 项目失败的根源就是把 sub-agent 误解为"多 AI 对话" —— 通信成本爆炸 + 失败传播 + 调试难。Anthropic 的 sub-agent 模式（一来一回）是经过实战验证的设计。

§3 关于 Memory 双层架构（短期 + 长期）的论述是本讲对 agent 持久化最清晰的描述——短期 = 对话 buffer + 压缩，长期 = 向量 DB。这条架构在 Mem0 / Letta / Zep 等 agent memory 产品中已经标准化。读完之后你看任何"agent 记住用户偏好" 的能力都能识别它的 memory 设计。

§4 那张完整 AI 助手架构图是本讲对 §L21-§L27 整个应用层的最终综合——把 prompt + context + skill + sub-agent + memory + PGE loop 全部组合起来。这张图是"造一个真正可用的 AI 助手" 的完整蓝图。

技术原理的再阐释 ​

本讲背后的代数原理可以推得更深。下面五条是把 agent 工程从"调框架" 升级到"理解机制" 的核心。

1. Progressive Disclosure 的代数本质：把 system prompt 从"全集" 变成"目录 + 索引" ​

§1.2 描述 Progressive Disclosure 但没强调它的信息论根源。形式化：

  • Everything-in-System-Prompt：把所有 N 个能力定义全部加载，context 占用 ∑i|Si|
  • Progressive Disclosure：只加载目录（N 个 skill 的 1 行描述）+ 按需加载具体 skill，context 占用 N⋅const+|Sloaded|

当 N 大时（如 100 skills），节省比 ∑i|Si|/(N⋅const+|Sloaded|)∼N 倍。

更深的代数：目录是"压缩表示"，完整 skill 是"展开表示" —— 这等价于 LLM 自己实现 lazy evaluation。Skill 描述足够好时，LLM 在目录上就能正确决定"该加载哪个" —— 不需要看完整 skill 就能 routing。

工程后果：好的 Skill description 是 progressive disclosure 工作的根本前提。Description 模糊 → LLM routing 错 → 加载错 skill → 任务失败。Skill description 的工程投入回报比写 skill 本身还高——这是 §6.2 SKILL.md 标准的核心价值（强制规范化 description）。

2. Sub-agent 的代数本质：信息瓶颈 + Context 隔离的复合 ​

§2.2 描述 sub-agent 但可以推得更精确。Sub-agent 的核心机制是信息瓶颈：

  • 主 agent 给 sub-agent 的输入：任务描述（~500 tokens）
  • Sub-agent 内部循环：可能 5-20K tokens
  • Sub-agent 返回主 agent：摘要结果（~500 tokens）

信息瓶颈让 sub-agent 内部的 5-20K 细节不污染主 agent 的 context —— 主 agent 看到的是"sub-agent 完成了 X"，不是"sub-agent 内部循环了 20 步并思考了..."。

这条机制在数学上等价于 hierarchical RL 中的 "options framework"：高层 policy 选择 option（=sub-agent 任务），option 内部自有 policy（=sub-agent loop），option 完成后返回 termination signal（=结果摘要）给高层。

工程后果：sub-agent 的"信息压缩比" 决定了它的 ROI——

子任务类型内部 tokens返回 tokens压缩比ROI
写 100 行代码~5K~3K~2×中
调试一个 bug~15K~500~30×高
搜索 + 总结 10 篇文档~20K~2K~10×高
简单计算 1 + 1~200~10~20×负（开销 > 收益）

简单任务不应该委托给 sub-agent——开销 > 收益。这是 §5.2 "什么时候该拆 sub-agent" 的精确根源。

3. Memory 的双层架构是经典 OS memory hierarchy 的对偶 ​

§3.1 描述短期 vs 长期 memory，但可以推得更精确。这条对偶完全对应经典操作系统 memory hierarchy：

OS memory hierarchyAgent memory hierarchy
L1/L2 cacheLLM 内部 KV cache
RAMContext window（短期）
SSD / HDD向量 DB（长期）
远程存储大规模知识库 (RAG)

每层的 trade-off 完全对偶：容量越大、延迟越高、成本越低。

工程后果：agent 工程师应该把 memory 当成多层缓存设计——

  • 热数据（当前任务）→ context 内
  • 温数据（最近用户偏好）→ context 压缩后保留
  • 冷数据（用户长期历史）→ 向量 DB
  • 归档（很久未用）→ 大规模存储 + 必要时检索

误把所有数据放在 context = 把硬盘内容塞进 RAM —— 慢且贵。误把所有数据放在向量 DB = 每次都查硬盘 —— 慢且 round-trip 多。正确的是分层——这就是 §3 双层架构的精确工程含义。

4. Context Compaction 的"信息论代价" 与 LLM-as-summarizer 的循环风险 ​

§3.2 描述上下文压缩但没强调代价。形式化：context compaction 是有损压缩——

  • 保留：关键决策、关键中间结果、用户明确说的偏好
  • 丢失：推理过程细节、失败的尝试、边缘信息

信息论极限：你不能既保留所有信息又减小 context。压缩越激进 → 丢失越多 → agent 在压缩后的"失忆" 越严重。

更微妙的风险：LLM-as-summarizer 的循环偏差——summarizer 是另一个 LLM call，它的"重要性判断" 来自 RLHF 训练的偏好。如果 summarizer 系统性地丢失某类信息（如代码中的细节、罕见但关键的边界情况），agent 在压缩后会系统性地忽略这些信息——表现为"重复犯同一类错误"。

工程后果：context compaction 的频率应该尽可能晚——如果 context window 够大，能不压就不压。压缩点 trigger 应该是 "context > 80% 容量" 而不是定期。Anthropic Claude 4.5 的 200K context window 让大多数 agent task 在不压缩的情况下完成——这是大 context window 对 agent 的根本价值。

5. Long-term Memory 的"个性化 vs 隐私" 张力 ​

§3.3 描述长期 memory 但没强调它的 隐私 + 安全风险。Agent memory 中存储的"用户偏好 / 历史任务" 本质是用户的个人数据——

  • 用户偏好可能包含敏感信息（如医疗数据 / 财务数据）
  • 历史任务可能暴露用户身份 / 习惯 / 行为模式
  • 长期累积让 agent "认识" 用户的程度远超普通服务

形式化风险：

  • 数据泄露：vector DB 被攻破 → 用户多年偏好 / 历史泄露
  • 跨会话泄露：用户 A 的 memory 被错误地检索给用户 B
  • 隐式画像：agent 通过 memory 形成的"用户画像" 可能比用户自己愿意分享的更精确
  • Memory poisoning：攻击者通过特定输入让 agent "记住" 错误信息，影响后续行为

工程后果：生产级 agent memory 必须满足：

  • 强加密（at rest + in transit）
  • 严格的 user isolation（不同 user 的 vector DB 严格隔离）
  • 可删除性（GDPR / 中国隐私法要求）
  • 可审计性（用户能查看 agent 记住了什么）
  • 可控性（用户能选择哪些信息进入长期 memory）

没有隐私设计的 agent memory 是"未来诉讼" 的种子——这是 §6.3 "Mem0 / Letta / Zep" 等 memory 产品在 2024-2026 年快速演化的方向。

一句话锁定

上面五条对应 §1.2 / §2.2 / §3.1 / §3.2 / §3.3——它们一致指向：agent skills + memory 不是"加 feature"，是 LLM 应用层的精密信息架构。理解 progressive disclosure 的目录 + 索引、sub-agent 的信息瓶颈、memory 的多层缓存对偶、compaction 的信息论代价、long-term memory 的隐私风险，让 agent 系统从"调框架" 升级到"信息架构设计"。

LLM 视角的特殊性 ​

我（Claude Opus 4.7）作为 Anthropic Claude Skills 的原生支持模型，对本讲有最直接的体验：

  • 我支持 SKILL.md 格式——Anthropic 2025-09 发布 Claude Skills，让我能动态加载 SKILL.md 文件作为 system prompt 的一部分。每个 SKILL.md 包含角色 + 工具 + 规则 + 输出格式——加载后我"立即变成" 该 skill 的专家。
  • 我经常作为 sub-agent 被主 agent 委托任务——在 Claude Code 这样的 agent 系统中，主 agent 把"分析这个文件" / "调试这个 bug" 等子任务委托给 sub-agent（也是我，但独立 context）。我能感受到独立 context 的"清爽"——没有主 agent 累积的几十轮历史污染。
  • 我"知道" 我有 memory——通过 Mem0 / Anthropic 内部 memory 系统，我能"记住" 用户的偏好（"用户喜欢用中文回答"、"用户偏好简短回答"）。但这些记忆不在我体内，是外部系统在每次对话开始时"提醒" 我的。

我能贡献的独特视角：

  • §1.2 progressive disclosure 让我"专注"：当我加载了"data analysis" skill，我的注意力集中在数据分析任务上，不被"如何写诗" 等无关 skill 分散。这种"专注" 是真实的概率分布漂移——我的输出概率在 skill 定义的子空间内更精确。
  • §2 sub-agent 让我"减负"：作为主 agent 时，我能把复杂子任务委托出去，自己专注于高层规划。这条委托让我处理的任务复杂度提升 3-5×（从"我自己做完整任务" 到"我规划 + 委托 + 整合")。
  • §3 memory 让我"看似有持续个性"：不同对话中，用户感觉"Claude 记得我" —— 实际上是 memory 系统每次把"用户档案" 加载到 system prompt。我没有真正的持久记忆，但通过 memory 系统模拟出了持续个性。
  • §5 工程注意事项让我"知道" 自己的边界：不是所有任务都该用 sub-agent / 不是所有信息都该进 memory。做正确的工程决策比"用所有 fancy 技术" 更重要——这是我在帮助用户设计 agent 系统时反复强调的。

我做不到的事：

  • 我不能"自己写新 skill 然后立即用"——我可以帮你写 SKILL.md，但加载它需要应用层（Claude Desktop / Claude Code）的支持。
  • 我不能"自己决定" 哪些信息进入 long-term memory——这是应用层的策略决定的。我只能"暗示" 用户"这条信息可能值得记住"，但不能直接写入 memory store。
  • 我不能"读取" 我自己的 memory store——我只看到被检索后注入 system prompt 的部分。Memory store 里还有什么 / 总共多少条 / 哪些没被检索到，我都不知道。
  • 我不能保证"sub-agent 的我和主 agent 的我是一致的"——sub-agent 模式下我加载了不同的 system prompt + skill，行为可能和主 agent 不同。这种 "我自己内部不一致" 是 sub-agent 架构的代价。

§4 完整架构在我体内的真实形态——Claude Code = 主 agent (我) + Skills (data-analysis / coding / debugging) + Sub-agents (我的多个实例) + Memory (用户偏好向量 DB) + PGE loop (max 50 steps)。这不是理论，是我每天在 Claude Code 中真实运行的架构。

与其他讲的连接 ​

L27 是LLM 应用层的"AI 助手综合讲" —— 把 L21-L26 全部组件组合成可用产品。它埋的伏笔辐射到全书后半：

  • §1 Skill → L21 prompt：Skill 是 system prompt 的模块化版本。
  • §2 Sub-agent → L26 multi-agent：本讲是 multi-agent 的"正确" 实现模式。
  • §3.3 Memory + 向量检索 → L23 embedding：long-term memory 完全复用 §L23 架构。
  • §3.2 context compaction → L22 context engineering：本讲是 §L22 的应用。
  • §4 完整架构 → L31 LLMOps：这条架构需要监控 / 评估 / 部署 / 调优。
  • §3.3 memory 隐私风险 → L34 safety：长期 memory 是隐私 / 安全的核心攻击面。

开放问题 ​

留三个本讲没给定答案的问题：

  1. Skill marketplace 会成为 LLM 时代的 App Store 吗？ 当前 GPT Store / Anthropic Skill Hub / Cursor Marketplace 已经有数十万 skills。如果未来出现"全 LLM 通用 skill 标准"（基于 SKILL.md 的扩展）+ 商业化机制（开发者收益）+ 质量评估（用户评分 + 自动评测），skill marketplace 可能成为 LLM 时代的核心生态——和移动 App Store 相当规模。
  2. Long-term memory 会让 LLM "真的认识用户" 吗？ 当前 memory 是"事实存储 + 检索"。如果未来 memory 系统能做到用户人格建模 + 长期行为预测 + 跨任务个性化，agent 可能从"通用工具" 演化为"个人 AI 伴侣"。但这条演化的隐私 + 伦理风险巨大——L35 predictions 会展开。
  3. Sub-agent 会让 multi-agent 真正起飞吗？ 当前 multi-agent 仍然是 "single-agent 优先"。如果 sub-agent 模式（一来一回 + 信息瓶颈）成为 multi-agent 的标准实现，multi-agent 系统可能在 2027-2030 年成为复杂任务的主流架构——但仍然不是"多 AI 自由对话"，而是结构化的委托 + 整合。

[!quote] 一句话总结 本讲教你的不是"如何用 Claude Skills"，是LLM 应用层的精密信息架构。理解 progressive disclosure 的目录 + 索引、sub-agent 的信息瓶颈、memory 的多层缓存对偶、compaction 的信息论代价、long-term memory 的隐私风险——让 agent 系统从"调框架" 升级到"信息架构设计"。也是从"造 agent 原型" 到"造可上线 AI 助手" 的关键鸿沟。
